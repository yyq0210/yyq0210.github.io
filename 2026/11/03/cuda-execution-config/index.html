11.1 Occupancy：SM 里住了多少 warp

先看从 grid 到执行的过程

调用 kernel<<<grid, block>>>() 后，grid 中的 block 不会全部同时驻留。GPU 将有条件运行的 block 分配到 SM；block 需要获得相应的寄存器、共享内存和线程等资源。已经驻留的 warp 也可能正在等待数据或同步。

理解这三个英文词很重要：

名称 含义 一个具体例子
Resident / active warp 已经驻留，资源已分配 warp 等待一次 global load 返回，依然驻留
Eligible warp 下一条指令当前可以发射 指令依赖已满足，没有被 barrier 阻塞
Issued warp 调度器实际选中它发射指令 这个调度机会选择了 warp 2

图中的漏斗表示条件逐步收紧，不是说 warp 只能沿单向路径走一次。一个 warp 在执行中会反复经历“可发射—发射—等待—再次可发射”。Nsight Compute 的 Scheduler Statistics 用 active、eligible、issued 等统计帮助观察这个过程。Nsight Compute Profiling Guide

Occupancy 的分母是架构上限

例如某个教学模型允许最多 64 个 warp，而当前有 24 个 warp 驻留，则 occupancy 是 24 / 64 = 37.5%。它没有回答这 24 个 warp 中有多少正在等待，也没有回答 Tensor Core 是否繁忙。

因此这三个判断都不成立：

  • occupancy 100%，所以每个周期都在做有用计算。
  • occupancy 25%，所以算力最多只能达到峰值的 25%。
  • kernel 在等待内存，所以 achieved occupancy 一定下降。

第三条特别容易混淆：等待不会自动释放驻留资源。 等待中的 warp 仍然可以被算进 occupancy。要定位等待，应继续观察调度器是否缺乏 eligible warp、发射是否有空隙，以及相关依赖或访存指标。

__launch_bounds__ 到底保证什么

256 是这个 kernel 声明支持的最大 block 线程数。第二个参数 2 提供期望的每 SM 最少驻留 block 数，编译器据此规划寄存器使用。

它不保证运行时一定驻留两个 block。例如一个 block 已占掉大部分 SMEM，即使寄存器满足条件，仍然可能只能驻留一个。编译器也不是只会减少寄存器：在约束允许时，它可能增加寄存器，以减少指令或改善延迟。强行限制寄存器还可能带来 spill。Launch Bounds 语义

理论 occupancy 和 achieved occupancy

指标 回答什么 常见影响因素
Theoretical occupancy 按资源配置，最多能驻留多少 block 大小、寄存器、SMEM、架构限制
Achieved occupancy 实际执行过程中，平均驻留了多少 grid 大小、调度过程、长短任务差异、收尾阶段

假设 kernel 资源允许每个 SM 驻留 4 个 block，但整个 grid 只有 20 个 block，而设备有 100 个 SM。此时不可能靠这个 grid 填满所有 SM。再如，大部分 block 很快结束，剩下一两个长 block，末尾便出现大量空闲资源。

这类供给不足和“已经驻留，但下一条指令不能发射”是不同问题。前者要看任务数量和负载平衡；后者要看依赖与延迟隐藏。

为什么 GEMM 每线程计算多个输出

假设每个线程维护一个 float acc[4][4]，对应 16 个输出元素。不同输出可以形成多条独立累加链，还可能复用已经加载的 A、B 元素。但 accumulator 越多，占用的寄存器也越多。

这里的 acc[4][4] 是逻辑写法，是否全部驻留寄存器取决于编译器和索引方式。若你把同一个求和拆成多个累加器，最后再相加，还会改变浮点运算顺序，需要重新核对误差。

11.3 Thread 与 block：大小、形状和工作量

128～256 是试验起点，不是标准答案

原文建议以 128～256 个线程作为初步探索的范围，并优先考虑 warp 大小的整数倍。它没有说每种 kernel 都应该使用 256 个线程。

256 个线程：(32,8) 和 (16,16) 一样吗

若 threadIdx.x 对应矩阵列、threadIdx.y 对应矩阵行：

  • block=(32,8)：warp 0 对应第 0 行的 32 列。
  • block=(16,16)：warp 0 对应第 0 行的 16 列，加第 1 行的 16 列。

于是同一个 warp 访问的地址集合可能改变，影响合并访存、SMEM bank 映射和计算分工。不能只因为形状是二维就判断性能，也不能仅凭线程总数就判断访存相同。 是否有差异，要把线程坐标代入实际地址公式。Thread hierarchy 与线程编号

一个大 block 与几个小 block 的取舍

假设两种设计分别用一个 1024 线程 block，或四个 256 线程 block 处理相同规模的数据：

设计变化 可能改善 可能付出的代价
拆成更小 block 更多独立调度单位；block 内同步影响范围缩小 重复加载、初始化增多；跨 block 无法直接共享普通 SMEM
合成更大 block block 内可共享更大的工作集 资源更难容纳；部分线程等待可能拖住整个 block
增加 block 数 小 grid 下更容易覆盖更多 SM 每 block 工作太少会增加固定成本

这些是需要验证的趋势，不是必然结果。注意 __syncthreads() 的作用域是 block；它不是整个 grid 的栅栏。

尾部效应

假设多数 block 用时很短，少数 block 很长。即使前半程有充足并行工作，最后也可能只剩少量 SM 忙碌。平均 achieved occupancy 会受影响，总耗时则由最后完成的工作决定。

针对这种情况，可以考虑让每个 block 的任务更均衡、拆分特别大的任务，或让持久化 kernel 动态领取工作。后者也有调度成本，不应仅为提高一个 occupancy 数字而采用。

11.4 Shared memory：复用与并发争用同一份容量

更多 stage 为什么可能更快，也可能更慢

在 GEMM 中，增加 stage 通常意味着保留更多输入 tile 的 buffer，以便提前搬运后续数据。假设每个 stage 占 16 KiB，忽略固定 SMEM，SM 可用 128 KiB，每个 block 为 128 线程，即 4 个 warp；最大 warp 数为 64，且其他资源暂不构成限制：

Stage 数 每 block SMEM 可驻留 block 数 驻留 warp 数 Occupancy
2 32 KiB 4 16 25%
4 64 KiB 2 8 12.5%
6 96 KiB 1 4 6.25%

这个表只计算容量，没有给出哪一行更快。可能出现两种相反情况：

  1. 原来每次计算都在等输入。增加 stage 后，输入提前准备好，Tensor Core 得以更连续工作，即使 occupancy 降低，时间仍缩短。
  2. 原来的预取深度已足够。继续增加 stage 无法进一步减少等待，反而挤掉其他 CTA 或带来额外管理成本，时间可能变长。

11.5 并发 kernel：stream 给出机会，资源决定能否重叠

两个独立任务放到不同 stream

NonBlocking 在这里主要涉及与 legacy default stream 的隐式同步关系，它不承诺两个 kernel 一定同时运行。可重叠还取决于设备能力、依赖、资源和调度。Stream synchronization behavior

默认 stream 还存在两种容易混淆的模式：legacy default stream 会与同一 context 中的其他 blocking stream 建立隐式同步；per-thread default stream 是每个主机线程自己的默认 stream，不具备前一种全局式隐式同步行为。如果程序混用两者，per-thread default stream 仍会与 legacy default stream 同步。排查“为什么没有重叠”时，应检查编译选项与库调用使用的默认 stream 模式。

图中的时间区间是示意。两个 kernel 的 block 可能在不同 SM 上运行，也可能在资源允许时共享某些 SM；stream 本身不预留某一组 SM。

哪些情况值得尝试

如果 A 只有很少的 block，设备还存在空闲资源，B 有机会利用这些资源。但若 A、B 都已能打满同一个带宽瓶颈，重叠可能只是争抢带宽，各自时间变长，总吞吐未必改善。

同样，“Tensor Core 暂时不忙”不意味着第二个 kernel 一定能进来。已有 block 可能仍占着寄存器、SMEM 和驻留槽位，导致新 block 无处驻留。

cudaDeviceProp.concurrentKernels 表示设备是否支持并发 kernel 能力，不能据此推算理想 stream 数，也不能保证指定任务组合重叠。

存在真实依赖时，要明确建立顺序

这个等待让 B 排在事件完成之后，同时不要求主机线程先阻塞等待 A。可以重叠的是其他没有依赖的工作，不能为了并发移除必要同步。CUDA asynchronous execution

测量整个任务组，而不是只看一个 kernel

对并发优化，应比较相同工作量全部完成所需的时间。不要把不同 stream 上互不关联的两个事件直接当作整个任务组的起终点。

可用一个协调 stream 记录起点，让工作 stream 等待起点；各工作 stream 完成后记录结束事件；协调 stream 等待全部结束事件，再记录总终点。这样显式建立计时范围。也可以使用 Nsight Systems 检查实际重叠与间隙。

11.6 Multiple contexts：别把 context 当成 stream

三层对象分别做什么

对象 可以怎样理解 不应该怎样理解
Host process CPU 侧应用及其资源 自动独占一张 GPU
CUDA context 管理设备侧资源、地址空间、模块与执行状态的环境 一条任务队列
CUDA stream context 中组织操作顺序的队列 专属 SM 或专属计算引擎

普通 Runtime API 使用通常涉及设备的 primary context；同一进程内使用该设备的库可以共享它。不要将 primary context 理解成“全机器所有进程共享的唯一 context”。在混用 Driver API 时，线程当前绑定的 context 也会影响操作归属。Primary context API

为什么一个应用不宜随意创建多个 context

假设主程序调用一个 CUDA 库，而库又创建自己的 context。现在同一应用可能存在重复的设备管理状态、分离的资源归属，以及额外的切换或协作成本。多个 context 并不会自然带来比多个 stream 更好的并行。

同一 context 可以被多个主机线程使用；使用 Driver API 时，各主机线程的 current-context 状态需要正确管理。对于同一应用内的并发任务，通常先考虑在已有 context 内使用多个 stream，而不是每个线程都创建一个新 context。

retain、push、pop、release 是不同操作

下面展示 Driver API 的作用关系，CHECK_CU 表示检查 CUresult 的工程宏：

push 改变当前主机线程的 context 栈；pop 恢复之前的状态；release 释放此前保留的 primary context 引用。实际工程需要保证错误路径也正确配对，并在释放引用前完成自身应完成的工作、处理资源生命周期。Driver API context 管理

多进程与 MPS

原文提醒普通多 context 使用中的时间片调度与切换代价。应将其放在相应运行模式下理解，不要推广为“现代 NVIDIA GPU 上所有不同 context 永远不能重叠”。

MPS 面向多进程客户端共享 GPU，可以提供跨进程的并发执行机会并减少部分调度开销，但不会创造额外的内存带宽、寄存器或计算能力。两个客户端争用同一瓶颈时，单任务延迟仍可能增加。MIG 则侧重硬件资源分区，是另一类机制。NVIDIA MPS 文档、NVIDIA MIG 文档

理论 / achieved occupancy 区分资源上限与实际驻留
Eligible warp、发射空隙及相关等待 判断是否缺乏可执行工作
计算管线、内存系统利用情况 查明资源是否接近饱和
Spill 与额外指令 检查压资源是否引入代价
kernel 时间或任务组完成时间 判断优化是否真正有效

对 Blackwell 的 TMA / UMMA kernel，还需要结合异步计算和搬运活动分析。warp 负责提交异步工作后进入等待，不等于计算引擎也在空转。单看一个 warp 指标或 occupancy 数字不足以解释整条流水线。

常见误解速查

常见说法 更准确的判断方式
Occupancy 越高越快 看新增驻留是否减少发射空隙，以及是否损失复用、ILP
寄存器越少越好 先看是否解除瓶颈，再看 spill 和指令增加
256 线程总比 128 好 对相同任务实测，检查资源、映射和同步
Block 形状不影响性能 形状本身不是结论；代入地址与计算映射看实际变化
Stage 越多越能隐藏延迟 深度足够后可能只增加资源占用
多 stream 必然并发 检查依赖、设备能力、驻留资源和实际时间线
多 context 等于更多并行 先明确应用资源归属，再选择 stream 或适当多进程机制
改用 TMA 没收益一定因为 occupancy 同时验证搬运、同步、计算、带宽与任务供给
