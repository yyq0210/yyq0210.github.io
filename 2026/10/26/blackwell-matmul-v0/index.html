Blackwell Matmul V0 完整图解：线程分工、Swizzle、寄存器分片与三级流水线

读 Tensor Core GEMM 时，难点往往不是矩阵乘法本身，而是同一个元素不断变化的“位置”：它在全局内存里由哪个线程搬运，进入共享内存后如何重排，最终又落在哪个 lane 的寄存器里？异步复制还没结束时，计算线程又该等谁？

本文沿着 matmul_v0.cu 的执行过程，把这些问题拆开。先确定 block 和 warp 的分工，再逐层展开存储布局，最后将数据搬运与计算放回三级流水线。全文配有 17 张图：12 张线程与存储布局图、3 张完整 SMEM tile 与 MMA 的对应图，以及 2 张流水线与同步图。

本文分析的是 gau-nernst/learn-cuda 的 matmul_v0.cu，固定版本 afcb20b1。它位于 Blackwell 教学目录，但采用的是 cp.async + ldmatrix + mma.sync 路径，可作为理解后续 TMA、tcgen05 和 TMEM 版本的基础。背景阅读见作者的 tcgen05 for dummies。

V0 的累加结果保留在线程寄存器中。这个版本没有使用 TMA、tcgen05 或 TMEM。

代码节选中有些常量已展开为默认数值，便于对照图片；完整源码快照见文末附件。除特别说明外，所有讲解都针对原始完整 tile 配置。

1. 先统一坐标，避免把 B 的两个视角混起来

默认配置：

层级 配置
一个 block / CTA 128 个线程，4 个 warp
一个 block 的输出 128×128
每轮 K tile 64
一个 warp 的输出 64×64
一次 warp 级 MMA 16×8×16
数据类型 A/B/C 存储为 BF16；acc 为 FP32
SMEM 每 stage 32 KiB，共 3 stages，即 96 KiB

约定：

  • tid 是 block 内线程编号，范围 0…127。
  • w = tid / 32；l = tid % 32。图里的 L5 是 warp 内 lane 5，T5 是 block 内线程 5。
  • wm = w / 2，wn = w % 2，确定 warp 在输出中的位置。
  • iter_k 是外层 K tile 编号；k=0…3 是这个 tile 内的 K=16 子块编号。
  • m=0…3、n=0…7 是一个 warp 内的输出子块编号。
  • 公式中的 / 都是整数除法。

这条 cp.async 实际做了什么？

shared.global 表示从全局内存复制到共享内存，末尾的 16 是字节数。dst_addr 是共享内存地址空间内的 32-bit 地址，src_addr 是全局指针；这也对应内联汇编中的 r 和 l 操作数约束。

.cg 选择 global 层级的缓存策略提示。更关键的是，这条复制指令不需要先把这 16B 数据作为普通 load 的结果放进线程寄存器，再由线程执行 shared store。线程负责提交复制，后续通过 group wait 确认完成。

一个 warp 的一次复制迭代覆盖 4 行，每行 64 个 BF16，即 4 段各 128B 的连续数据。全局矩阵的一行可能远长于 64，所以不能把这 4 段误读成全局地址上连续的一整块 512B。

为什么按 16B 包做 XOR？

可以用共享内存的 bank 索引解释这个布局。对本文的 BF16 配置，采用 32 个 bank、每个 bank 对应 4B 字的地址视角：

若每行都是普通的 128B stride，同一列包在连续 8 行上会反复落到同一组 4 个 bank。例如第一个包的 8 行都使用 bank 0…3。

swizzle 后，逻辑 pack 0 在第 r=0…7 行上的物理 pack 为 r：

行 物理 pack 包占用的 bank
0 0 0…3
1 1 4…7
2 2 8…11
3 3 12…15
4 4 16…19
5 5 20…23
6 6 24…27
7 7 28…31

这样，同一张 8×8 小矩阵的 8 个 16B 行段就分散到了不同的 bank 组。这里解释的是这套地址布局的作用，不意味着任意访问方式套上 XOR 都会更快。

代码先用 __cvta_generic_to_shared 把通用指针转换为共享地址空间地址，再用整数做字节偏移。因此 A_smem + 128 表示加 128B；它与 BF16 指针 A + 128 表示加 256B 是两种不同的运算。

8. MMA 的结果放在哪里？每个线程写回哪里？

指令中的各段如何对应数据？

可按顺序读成：warp 级协作 MMA，形状 M=16、N=8、K=16；A/B 使用 row/col 分片格式；输出 D 为 FP32，输入 A/B 为 BF16，输入累加器 C 为 FP32。数学操作是 D = A×B + C。

源码让 D 与 C 使用同一组 C[0…3] 寄存器，因此每次调用都会原地更新 acc。内联汇编的 +f 表示这些 FP32 操作数既读取又写入；A/B 的 r 则传入 packed BF16 的 32-bit 位模式。

这里的 .sync 是 warp 指令的协作语义，不能代替等待异步复制，也不能让另一个 warp 自动到达相同程序位置。.aligned 也不能用来推导任意线程分支都能合法调用它；本代码由参与的整个 warp 一致执行。

一条 mma.sync.m16n8k16 为整个 warp 更新一个 16×8 输出子块。

默认参数下，compute(iter_k) 可以概括成以下三段。下面强调循环结构，地址构造仍以前文为准：

每轮 K tile、每个 warp 的数量关系是：

操作 次数 覆盖的数据
A 的 ldmatrix.x4 16 64×64 BF16
B 的 ldmatrix.x4 16 64×64 BF16
mma.m16n8k16 128 64×64 输出沿 K 累加 64

这些是 warp 级指令次数。32 个 lane 共同执行同一条 MMA，不能再乘 32 当成 32 个独立矩阵乘法。

用 FLOP 数可交叉核对：每次 MMA 是 2×16×8×16=4096 FLOP；每 warp 每轮为 128×4096=524,288 FLOP；4 个 warp 合计 2,097,152 FLOP，恰好等于 2×128×128×64。

acc 在进入 K 循环前统一置零，compute 内不会重新清零。因此每轮都接着前面 K tile 的结果继续累加，直到最后统一写回 C。

结果在哪里？它一直留在同一个 acc 子块

acc[1][2] 是源代码视角下 每个线程自己的 4 个 FP32 值。32 个 lane 合起来才形成完整 16×8 输出块，既不是单线程拥有一整块，也不是在 SMEM 或 TMEM 中另开了一块输出矩阵。

本次 k=2 的结果不会单独存回 SMEM。它加到原有 acc 上；k=3 和后面的外层 K tile 继续更新同一组累加器。所有 K 完成后，才将这些 FP32 结果转换为 BF16 写到全局 C。

全部 128×128 输出怎样覆盖？

固定 k，一个 block 需要把 8 个 A 行子块与 16 个 B 行子块两两配对，得到 8×16=128 个输出子块的新增贡献。每个 warp 负责其中一个 4×8 象限。

四个 k 合计：

所有输出子块共同覆盖 128×128 的 C。数据复用同时发生：同一个 A(u,k) 被 16 个 v 使用，同一个 B(v,k) 被 8 个 u 使用。跨 warp 时，同一份 SMEM 数据会分别加载到相关 warp 的寄存器中。

若全局 K=4096，外层有 4096/64=64 个 stage 使用轮次，每个 block 总共执行 64×512=32,768 次 warp 级 MMA。SMEM 的物理槽位始终只有 3 个，按 iter_k%3 循环复用；输入数据不断更新，acc 则持续保留到最后。

要查任意一次调用的全部范围，可用附件 单个 stage 的 512 次 MMA 输入与输出对应表。表中区间使用左闭右开格式；外层轮次只需给 K 范围加 iter_k*64，并选取对应 stage 的 SMEM 基址。

12. 三级流水线：把未来的复制和当前的计算重叠

load_AB 与 compute 的分工

load_AB(j) 把第 j 个 K tile 复制到 stage=j%3。A/B 全局指针在每次调用后前进 64 个 BF16，因而这段实现依赖 load_AB 按 0,1,2,… 的顺序调用。

这段是省略参数的流程示意。一次调用中，每线程提交 8 条 A 复制和 8 条 B 复制，然后 commit 成这个线程的一个 group。group 是每线程的复制批次，stage 是全 block 共享内存中的物理槽位，两者不是同一个对象。

compute(j) 从 j%3 槽位读到寄存器，并执行当前 K tile 的 MMA。这里没有专门的 producer warp：同一批线程轮流负责提交复制、等待、读寄存器和计算。

预热：为什么先提交两轮？

3 个槽位提供三个不同 tile 的存放空间。先准备两个，进入第一轮后再提交 tile 2，便能在等待 tile 0 时保留两个更晚的预取批次。这里的三级缓冲描述存储容量和提交窗口，不保证任一时刻一定有三次未完成传输。

两个 __syncthreads() 为什么都需要？

图 16：两处 block barrier 的作用。

循环顶部的 barrier 把各 warp 的进度对齐：较快的 warp 不能提前开始复用 SMEM，而其他 warp 还在读旧内容。源码的注释写了 wait MMA，但它不是一个 tcgen05 异步 MMA 完成对象；在本实现中，各线程从 compute 走出来后到达普通 block barrier，消费旧数据的阶段已经过去。

wait_group 后的 barrier 用于合作读取：一个线程等待的是自己提交的复制，而 ldmatrix 要读取整个 warp、甚至由其他 warp 的线程写入的共享 tile。所以各线程先完成自己的等待，再通过 block barrier，之后才能一起使用当前数据。

两个操作不能互相代替：只做普通 block barrier 并不能据此断言 cp.async 已经完成；只做每线程的 group wait，也没有完成这里所需的全 block 协作同步。

为什么最后两轮需要提交空 group？

当真实 tile 都已经提交，仍有最后两轮 compute 要执行。源码没有继续加载越界 tile，而是这样排空：

以图中的 6 个 tile 为例：真实组为 G0…G5。提交 E0 后，最近两组成为 G5/E0，因此 G4 必须完成；再提交 E1，最近两组变为 E0/E1，因此 G5 也必须完成。

空组本身没有数据搬运，但仍然占据“最近提交的组”序列中的位置，所以固定的 wait_group 2 也能逐步覆盖最后两个真实组。不能仅凭“现在最多剩两次未完成复制”就跳过这个排空过程。

哪些工作真正发生重叠？

重叠的主要对象是未来 tile 的异步 GMEM→SMEM 复制，与当前 tile 的 SMEM→寄存器读取及 MMA。compute(i) 的源代码仍按加载 A、加载 B、MMA 的顺序组织；不能从三级缓冲直接推导出三次 MMA 在同一 warp 内异步并行执行。

这也解释了为什么 V0 不需要像后续 tcgen05 实现那样，为异步 MMA 单独维护一组 mbarrier：这里使用的是不同的计算指令与完成机制。

14. 读完源码后，需要保留的适用范围与性能判断

这是完整 tile 教学 kernel

原实现没有为复制、读寄存器和输出写回增加尾块掩码。默认使用时需要完整的 M/N=128 和 K=64 分块；预热固定提交两个 K tile，因此这套原始流程还要求至少两个完整 K tile，即 K>=128。

host 的 grid 使用向下取整，kernel 内部却用 cdiv(N,128) 计算二维坐标。它们在 N 可整除 128 时一致，不能据此认定非整除尺寸也已经得到支持。cdiv(K,64) 同样不等于末尾越界加载自动安全。

三级缓冲与寄存器复用都有资源成本

96 KiB 动态 SMEM 会影响一个 SM 上可同时驻留的 block 数，但不能只凭这一项判断实际 occupancy。输入分片和 acc 的逻辑数组也很大，需要结合编译器报告、寄存器分配及 spill 情况分析。

代码中显式列出的数据量能解释成本来源，实际快慢则仍需 GPU 实测。本文没有给出未经测量的 V0 TFLOPS，也不把此前 V1–V4 的成绩套用到 V0。

从源码可以确定的是：每线程要提交多条小粒度 cp.async、计算 swizzle 地址、持有 A/B 分片并执行多个 warp 级 MMA。这些工作正是理解后续 TMA 和 tcgen05 路径时值得对照的环节。

阅读 V0 时最值得记住的四个区分

容易混在一起的概念 本文对应关系
搬运线程与计算线程 同一批线程参与两种工作，但输入搬运坐标和输出分片坐标不同
地址提供者与数据接收者 ldmatrix 的 lane 地址输入与寄存器输出分发是两套规则
数据布局与同步顺序 swizzle 决定数据放哪里；group wait/barrier 决定何时可以使用
stage 与 group stage 是可复用存储槽；group 是某线程提交的一批复制指令

15. 图中布局如何校验，如何查询任意线程

配套脚本先按 cp.async 的实际索引建立 SMEM 字节地址模型，再按源码的 A_addr ^ (k*32)、B_addr ^ (k*32) 建立地址提供者，最后依据 ldmatrix 的分发规则还原各 lane 寄存器，并与 MMA 输入坐标逐项比较。

本次 CPU 地址模型校验通过：

  • 3 个 stages 的 A/B 共 49,152 个 BF16 地址无重叠且完整覆盖。
  • 4 个 warp、全部 K/M/N 子块共 98,304 个寄存器元素映射与预期一致。
  • 输出的 16,384 个坐标恰好各写一次。
