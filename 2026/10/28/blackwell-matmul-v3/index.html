Blackwell GEMM 流水线入门：图解 matmul_v3 的双缓冲、barrier 与 phase

matmul_v2 已经使用 128B TMA 切片与 swizzle，但仍然先等搬运、再等计算。matmul_v3 的下一步是：保留两份 SMEM 输入缓冲，提前搬运下一块 K 数据，让 TMA 与当前 MMA 有机会重叠执行。

本文沿着实际源码解释从 host 初始化、预取、主循环到收尾的过程，重点回答一个容易混淆的问题：**为什么两个 buffer、两个 TMA barrier，却只需要一个局部 tma_phase 变量？**最后附 B300 本地 1039 TFLOPS 的实测记录及教程 B200 对比。

源码作者为 gau-nernst。本文依据固定提交 afcb20b1bd89065c31a1575c276aba686fc4dfce 编写，图解和调度推导独立整理。配套包包含 PNG、可编辑 SVG、源码快照和 CPU 调度校验脚本，不依赖 Mermaid。本文未重新运行 GPU benchmark；本地性能来自作者提供的运行记录。

仍然是 BF16 输入、FP32 累加、BF16 输出。A 的物理形状为 [M,K]，B 为 [N,K]，C 为 [M,N]，数学计算是 C=A×Bᵀ。

2. stage 到底是什么：一份可复用的 A/B 输入缓冲

NUM_STAGES=2 表示准备两份输入数据区。stage 不是线程、warp 或一份独立输出。

每份 stage 内先放 A，再放 B；两份 stage 连续存储：

每个槽位有自己的生命周期：空闲 → TMA 写入 → 数据就绪 → MMA 读取 → 计算完成、可复用。源码通过固定调度和 barrier 保证这些顺序，不需要显式创建一个状态枚举。

3. host 初始化、grid 与线程角色

host 为 A/B 分别调用 init_tmap_3d_128B()。与 v2 相同，128B swizzle 已在这个函数内部编码，不需要在调用处再次传 swizzle 参数。

本例 TMA box 的最内维仍为 64 个 BF16，即 128B；因为 BLOCK_K=128，第三维的宽切片数是 2：

维度顺序为最快变化维在前。A 的 globalDim 为 {64,M,K/64}，globalStrides 为 {K×2,128} 字节；B 使用 N 作为高度。

launch 分配的动态 SMEM 为 (BLOCK_M+BLOCK_N)×BLOCK_K×NUM_STAGES×2。barrier 和 TMEM 地址槽是另行声明的静态共享元数据；192 KiB 指 A/B 动态数据区。

grid 仍为 (M/128)×(N/256)。kernel 内通过 bid_m=bid/grid_n、bid_n=bid%grid_n 还原二维输出 tile 坐标，并计算 off_m/off_n。

工作 执行者

elect_sync() 的作用是避免重复发起整块操作。虽然控制指令由同一个 warp 发出，TMA 引擎和 Tensor Core 可以异步工作，因此不要求两个 warp 分别控制它们才能重叠。

4. 两个 TMA barrier、一个 MMA barrier，各自跟踪什么

源码声明：

两个输入 stage 各有一个 TMA barrier。每个 barrier 都有独立的硬件状态；一个 stage 里 A 和 B 的搬运共同向该 stage 的 barrier 报告完成。

MMA 只需要一个 barrier，因为外层每次发起一组 MMA 后都会等待它们完成，再发下一组。本文中的“一组”指一个 BLOCK_K tile 内的 8 条 MMA。

对象 默认数量 意义
SMEM 输入 stage 2 存放当前 / 未来 A/B
TMA barrier 2 各自记录对应 stage 的搬运完成情况
MMA barrier 1 记录当前这一组 MMA 是否完成
tma_phase 每个线程一个局部变量 当前 TMA wait 的预期 parity
mma_phase 每个线程一个局部变量 当前 MMA wait 的预期 parity

barrier 初始化 arrival count 都为 1。等待线程有 128 个，并不意味着 count 应设为 128：wait 与 arrive 是不同操作。

fence.mbarrier_init.release.cluster 发布初始化，随后 __syncthreads() 让线程在使用 barrier 和分配返回的 TMEM 地址前完成同步。

每个 barrier 对象是 8B，且这里 mbar_addr 是原始字节地址，所以 tma_mbar_addr+stage_id*8 是选择 barrier。它不同于选择矩阵缓冲的 smem+stage_id*98304。

**load 的结尾没有等待搬运完成。**控制流继续向后执行时，TMA 硬件可能仍在搬运。这是后续重叠的前提。

6. compute(iter_k)：等待当前槽位，然后发起 MMA

compute 也先用取模确定 stage。它等待的是当前 tile 对应的 TMA barrier，而不是全部 barrier，也不是刚刚预取的未来 tile：

wait 完成后，通过 tcgen05.fence::after_thread_sync 建立后续 tcgen05 操作的顺序要求，再从该 stage 的 A/B 地址发起 MMA。fence 不替代 wait，不能仅保留 fence 就认为搬运已经完成。

compute 的末尾把当前组 MMA 的完成通知 commit 到唯一的 MMA barrier，但它自己不在末尾等待 MMA。**compute 返回代表发起工作，不代表计算已经完成。**外层循环负责真正的 MMA wait。

7. 为什么两个 buffer 只有一个 tma_phase

这里必须区分“每个 barrier 的硬件状态”和“线程给 wait 传入的期望值”。

两个 TMA barrier 的硬件状态始终独立。局部 tma_phase 只表示：当前消费的这个 stage，应该确认哪一代搬运已经完成。

程序按 tile 顺序消费，stage 顺序固定为 0→1→0→1。每个 stage 的使用次数因此可以从 iter_k 推导，不需要单独保存一个 phase 数组。

7.1 一个局部 phase 不代表两个 barrier 现在状态相同

预取是异步的，某个未来 stage 的 TMA 可以提前完成。比如 compute(1) 正在等待 barrier 1 的 phase 0，而 load(2) 对 barrier 0 的第二次搬运可能已经发起，甚至完成。

此时线程仍可使用 tma_phase=0 等待 barrier 1。这不要求 barrier 0 的实时状态也为 0。

**期望参数只针对本次选中的 barrier；它不是所有 barrier 状态的汇总快照。**用当前 stage 编号和预期代数共同决定等待对象，才是完整含义。

9. 首次不累加：stage 回到 0，不表示累加器要清零

每轮第一条 MMA 仍把 iter_k 作为零/非零的累加开关。只有整个 K 归约的第一条，即 iter_k=0 且片内首条，才不读取旧 TMEM 值。其他 MMA 都累加。

stage_id 回到 0 只意味着复用输入槽位，与输出累加器初始化无关。不能把首次累加条件误写为 stage_id!=0。

源码先单独发出第一条，再发 k2=1、2、3，最后处理 k1=1 的四次 MMA：1+3+4=8。同样可以用 j=0…7 的单层循环，其中 k1=j/4、k2=j%4；地址与累加规则保持不变。

11. 为什么顺序调用的 load 和 compute 可以重叠

load(i+1); compute(i); 的含义不是“等下一块搬完，再算当前块”。准确的执行步骤是：

如果当前数据已经可用，而下一块仍在搬运，那么硬件可同时执行：

两个操作访问不同的输入槽位。控制代码顺序提交指令，并不要求两个专用引擎串行执行到完成。

不过“有重叠机会”不等于每次都完全重叠。若当前 TMA 尚未完成，compute 会等待；若未来 TMA 很早结束，后续没有需要继续隐藏的搬运；流水深度、带宽和计算时间都会影响实际效果。

操作 本例的角色 不应误解为
TMA 发起 提交搬运请求 搬运已经完成
arrive.expect_tx 设置完成字节数并执行 arrival 一次普通线程同步

输出指令描述符仍指定 BF16 A/B、FP32 累加和 M=128、N=256。等所有 K tile 都完成后，epilogue 才读取最终结果。

TMEM 地址形式仍为 taddr+((warp_id*32)<<16)+n*8。.32x32b.x8 在这里让每个 lane 每次读取其对应行的 8 个 FP32，wait::ld 后转成 8 个 BF16，打包 16B 写回 global C。

每个线程负责 off_m+tid 行，共循环 BLOCK_N/8=32 次。线程内部的 8 个元素连续，但相邻 lane 写的是不同输出行，所以不能仅根据 int4 store 就称为完全合并的跨 warp 写入。

最后 __syncthreads() 确保所有线程读完 TMEM，再由 warp 0 协同释放。源码第 161 行的“store to smem”是旧注释，实际目的地是 C_ptr 指向的 global memory。

15. 适用边界与常见误读

15.1 stage 多不等于越快

本例双缓冲使用 192 KiB 动态 SMEM。保持 BLOCK_K=128 而直接把 stage 改为 3，会需要 288 KiB 的 A/B 数据区；不能忽略设备的每 block 资源上限。增大 stage 还会影响资源占用、调度和预取开销，性能需要实际测试。

15.2 源码没有自动处理所有短 K 和尾部形状

默认实现要求 M 是 128 的倍数、N 是 256 的倍数、K 是 128 的倍数，输出没有通用尾部掩码。

对一般 S-stage，原三段循环还要求 T=K/BLOCK_K 至少为 S−1，且至少有一次有效计算，即 T>=max(1,S-1)。否则可能预取超出逻辑 tile 数，或让收尾循环从负数开始。默认 S=2 下至少需要一个完整的 K tile。

15.3 两个 buffer 并不等于两个 TMA 永远在同时传输

NUM_STAGES 指可用于预取/消费的缓冲深度，不保证任意时刻恰好有 S 项搬运未完成。TMA 可能提前完成，多个请求也不保证在所有内部资源上完全并行。

15.4 v3 不是 warp specialization

它仍由 warp 0 elected thread 顺序发起 load 和 compute。异步引擎允许重叠，不需要单独 producer warp。下一版才会进一步拆分控制角色；本文不把下一版的每-stage MMA barrier 机制混入 v3。

15.5 phase 不是 buffer 编号，也不是“是否有数据”

buffer 编号是 iter_k%S，TMA 等待 parity 是 (iter_k/S)%2，MMA 等待 parity 是 iter_k%2。三个值可以不同。只保存 parity 能成立，依赖当前调度不会跨代误用，并正确等待再复用。

本次新增记录为 v3 的 1039 TFLOPS，未提供独立的实测延迟。本文不把由吞吐反算的时间冒充计时输出，也没有在整理时重跑 GPU。原始数值附件：benchmark.csv、environment.json。

16.2 教程 B200 与本地 B300

教程 B200 环境记录为 PyTorch 2.9.1 + CUDA 13，矩阵同为 4096³。原文 v3 为 939.61 TFLOPS，取整即用户对照表中的 940。

kernel B200 教程 TFLOPS B300 本地 TFLOPS 本地相对 CuBLAS
CuBLAS 1506.74 1673 100%

吞吐变化：

吞吐提升 36% 不等于耗时减少 36%。相同工作量下，由吞吐比推得的耗时比例约为 764/1039=73.53%，即减少约 26.47%。这只是固定工作量的换算，不是新增延迟实测。

原文性能来源：Pipelining 性能表。本地和教程都观察到 v3 相比 v2b 进一步提升，但软件版本、运行环境和计时细节并未完全控制；不能将 B200/B300 差异全部归因于单一硬件因素。

v3 相比 v2b 同时改变了 BLOCK_K 和 stage 数，表中的 +36% 是整个版本变化的测量结果。要单独隔离重叠、K 分块、TMA 发起开销等因素，还需要额外实验或 profiling。

17. 调度校验、源码导航与附件

配套 verify_pipeline.py 是 CPU 上的顺序调度模型，不启动 CUDA。它检查默认参数及多组合法 stage/tile 组合：

  • 每个 tile 恰好 load、compute 一次，K 区间没有漏算或重复。
  • 复用槽位前，该槽位旧 tile 的 compute 已经完成等待。
  • 当前 compute 消费的槽位确实存放对应 tile。
  • 单个 tma_phase 与每-buffer phase 数组，以及由 iter_k 推导的 parity 一致。
  • MMA phase 每轮翻转，与唯一 MMA barrier 的复用次数一致。
  • 原始预取、主循环、收尾边界与调度计数正确。
  • stage A/B 地址范围、MMA 地址及首次累加条件一致。
  • B300 +36.0%、相对 CuBLAS 62.1% 等数值计算一致。

模型验证不模拟 GPU warp 调度、内存可见性或硬件 barrier，实现层面的正确性和性能仍需 GPU 测试。结果见 verification.json，默认 32-tile 调度轨迹见 schedule.csv。
