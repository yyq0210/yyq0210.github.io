从 16B 到 128B：图解 Blackwell TMA Swizzle 与 matmul_v2

在 Blackwell GEMM 中，TMA 负责把 A/B 从显存搬入 shared memory（SMEM），tcgen05.mma 读取 SMEM 并将结果累加到 tensor memory（TMEM）。本文围绕 gau-nernst 的 128-byte global load and swizzling 一节，逐段解释 matmul_v2.cu，并从具体元素出发推导地址公式、LBO/SBO 和 k1/k2。

v2 的变化是：将 SMEM 中每行的切片宽度从 16B 扩大到 128B，同时让 TMA 和 MMA 使用一致的 swizzle 规则。计算的数学含义、MMA 的 K 宽度和最终输出布局保持不变。

源码作者为 gau-nernst；本文图解、数值推导和讲解独立整理。本地 B300 测试结果见第 19 节。本文按固定提交 afcb20b1bd89065c31a1575c276aba686fc4dfce 的源码解释，避免 main 更新后行号漂移。配套包包含 PNG 插图、可编辑 SVG、源码快照和 CPU 地址校验脚本；不依赖 Mermaid 或数学公式插件。

1. 先统一形状、单位和三个不同的“宽度”

源码的两个入口都采用以下配置：

A 的物理存储形状是 [M,K]，B 是 [N,K]，两者都沿 K 连续。输出 C 为 [M,N]，数学计算为 C = A × Bᵀ。不要把这里物理存储的 B 当成普通行主序的 [K,N]。

每个 block 负责 C 中一个 128×256 的区域。每轮沿 K 搬入 256 个元素：A tile 是 128×256，B tile 是 256×256，两者都是 BF16；累加结果为 FP32，写回 C 前转为 BF16。

名称 BF16 元素数 字节数 本文中的用途
swizzle 小包 8 16B 本节模式整体重排的最小单位
v1 每行切片宽度 8 16B 无 swizzle 的窄切片
v2 每行切片宽度 64 128B 128B swizzle 的宽切片
一条 MMA 的 K 宽度 16 32B 一条指令参与计算的归约区间
一轮 iter_k 的 K 宽度 256 每行 512B 一轮 TMA 搬运与 MMA 累加的范围

**TMA 搬多宽、swizzle 按多大单位移动、MMA 一次算多宽，是三个不同的概念。**将 TMA 宽度改为 128B，不会把 MMA_K 改成 64，也不会让一条 MMA 完成整个 K=256 的归约。

标题里的“128-byte global load”强调这里选择的连续搬运宽度。一条 TMA 并非只能搬 128B：本例一条 2D TMA 搬 A 的 16 KiB 或 B 的 32 KiB；一条 3D TMA 则搬完整 A tile 或 B tile。

3D TMA 的指令数前后都是 1，也不意味着内部搬运代价相同。Tensor map 描述的数据布局同样会影响性能。更宽切片有利于形成高效访问，但不能只根据指令数断言性能。

3. Swizzle 为什么能帮助 shared memory 访问

Shared memory 有 32 个 bank，相邻的 32-bit word 分配到相邻 bank。对本节的理解，可以使用：

如果直接将每行宽度扩大成 128B，又按普通行主序放置，那么相邻行的相同列相差 128B=32×4B，会再次映射到同一组 bank。例如每行开头的 16B 都落在 bank 0–3。

当访问模式需要同时读取不同的行、相同逻辑位置的数据时，就可能产生 bank 冲突。Swizzle 将不同的行以不同方式排列到 bank 上，从而分散这类访问。

这是一种用于解释“宽行为什么需要重新安排”的访问示例，不表示 v1 的合法窄切片布局本来就有同样的冲突，也不是对任意指令都承诺“开启 swizzle 就没有冲突”。实际效果取决于访问模式与事务划分。CUDA Shared-Memory Bank Swizzling

4. 128B swizzle 实际重排的是什么

本节使用 16B atomicity 的 128B swizzle。一行 128B 分成 8 个 16B 小包，每包 8 个 BF16。小包整体移动，包内的 8 个元素顺序不变。

在源码的切片起点满足 1024B 对齐时，可以把规则写成：

^ 是按位异或，不是乘方。例如 1^1=0，2^1=3。下图格子里的数字是逻辑小包号，横向位置是物理小包位置。

逻辑小包 0 在第 0–7 行分别落到物理包 0–7，对应 bank 0–3、4–7、……、28–31。原本集中在一组 bank 的这种跨行访问因此被分散。

两个重要条件：

  • 行宽在这个推导中恰好为 128B；不能把 pack ^ (row%8) 不加修改地套到任意行宽。
  • 基址按 1024B 对齐，使初始 swizzle base offset 为 0。本例 A/B 的切片大小也都是 1024B 的整数倍。换成非零 base offset 时，必须考虑起始模式偏移。

Swizzle 改变的是 SMEM 地址映射，不是 A/B 的逻辑元素，也不会改变矩阵乘法的数学结果。PTX Tensor Swizzling

4.1 原文的 32B、64B 图为什么不能简单按“每行 XOR 行号”套用

原文还讨论 32B 和 64B 模式。常用 TMA box 最内维宽度分别选为 32B、64B、128B；官方限制是最内维不能超过相应 swizzle span，并不要求所有应用都恰好等于 span。本文 kernel 恰好选满 128B。

原文更新特别指出：这些标准模式用于计算重排的“行号”，应从 128B 的物理地址分组理解。32B 或 64B 的 TMA 逻辑行，不能直接当成 128B 模式里的行。本文只对每行 128B 的 v2 使用简化 XOR 公式。

CuTe 的 Swizzle<3,4,3> 可理解为：保留最低 4 位，即 16B 小包内部的字节位置；用更高的三位影响小包位置。对零 base offset、以字节计的本例布局，可写出等价地址变换 x ^ ((x >> 3) & 0x70)。不必先掌握完整 CuTe 布局代数，才能读懂本例。

4.2 对照原文的 canonical layout 表

将一个 16B 小包看作规范化单位，K-major 布局的基础行距会随模式变化：

模式 canonical layout 中基础行距 对应的 8 行区域

32B swizzle 32B 8×32B
64B swizzle 64B 8×64B

5.2 TMA 发起时为什么没有额外的 XOR

Tensor map 已经包含源地址、源形状和步长、box 形状、swizzle 模式。tma_2d_g2s() / tma_3d_g2s() 调用只需要提供描述符、源坐标、SMEM 目的地址和 barrier 地址。

TMA 硬件读取 tensor map 后，直接按规定的 swizzle 写入 SMEM。不需要在搬运后再启动 CUDA 循环交换元素。

7. 为什么 v1/v2 的 LBO 和 SBO 不一样

LBO/SBO 属于 MMA 的 SMEM descriptor，用来解释输入矩阵的布局。下面仅讨论本例 K-major、相对偏移模式；不要把这套解释直接推广到 MN-major 或其他模式。

7.1 SBO：跨过一组 8 行

K-major 的 SBO 是从前 8 行跨到后 8 行的字节距离。

v2 中 row 0 和 row 8 的 XOR 模式相同，因此同一逻辑小包跨过这 8 行，偏移正好增加 1024B。

**SBO 不是整个切片大小。**v2 的 A 切片包含 128 行，占 16384B；SBO 只跨 8 行，占 1024B。B 切片有 256 行，占 32768B，但其 SBO 仍是 1024B。

7.2 v1 的 LBO：寻找相邻的 16B 逻辑小包

一次 BF16 MMA 沿 K 使用 16 个元素，即 32B。v1 每个切片只有 8 个元素，即 16B，所以一次 MMA 要取两个窄切片。

同一行的两个小包，物理上隔着一个完整切片。例如 A 的 A[0,0] 与 A[0,8] 相差 2048B：

MMA descriptor 需要告诉硬件如何从第一半 K 找到第二半 K。这就是 v1 的 LBO=height*16。

7.3 v2 不再通过 LBO 字段指定这段跳转

在 v2 中，一个宽切片每行已经包含 8 个 16B 小包。相邻逻辑小包的物理关系由规范的 swizzled layout 决定。PTX 对此处 K-major swizzled layout 的定义是：LBO 不使用，隐含为 1。

源码的“implied to be 1”不是说两个 BF16 相隔 1B。规范在该定义中把元素归一化为 128-bit，即 16B 单位；最终地址还要应用 swizzle。不要因此往 descriptor 填一个 1B 的 LBO。

更不能认为 swizzle 后相邻逻辑包的物理距离总是正向 16B：第 1 行的物理顺序为逻辑包 [1,0,3,2,5,4,7,6]，从逻辑包 0 到包 1，物理地址反而减少 16B。

A 的 LBO 2048B 本例模式不使用该字段
B 的 LBO 4096B 本例模式不使用该字段
SBO 128B 1024B
swizzle 无 128B，16B 小包

12. 准备 SMEM、barrier、TMEM 与 instruction descriptor

12.1 SMEM 分区和地址单位

动态 SMEM 声明为按 1024B 对齐的字节数组。__cvta_generic_to_shared() 将通用地址转换成 shared 地址；这里保存到 int 的 A_smem/B_smem 是字节地址。

这也是为什么 A_smem + ... 直接加字节数，不能再乘一次 sizeof(BF16)。与之相对，输出的 C_ptr 是 nv_bfloat16*，C++ 指针加法按 BF16 元素计数。

12.2 barrier 和 TMEM 地址槽

mbars[1] 是 SMEM 中的 64 位 barrier 对象；tmem_addr[1] 是 SMEM 中存放 TMEM 分配结果的 32 位地址槽。它们不是存放矩阵数据的同一块逻辑区域。

初始化 barrier 的 arrival count 为 1，因为每阶段的发起/完成协议只要求对应的一次 arrival；等待的线程有 128 个，不意味着 arrival count 必须是 128。

fence.mbarrier_init.release.cluster 发布 barrier 初始化，使异步访问者能看到它。随后 __syncthreads() 让整个 CTA 在使用已初始化对象和 TMEM 地址前完成同步。

12.3 分配 TMEM

分配参数为 BLOCK_N=256 列，程序使用 128 行、每元素 32-bit 的 TMEM 累加器，即 128 KiB 的逻辑数据容量。

源码注释说 taddr 在本例会是 0，但正确的使用方式仍然是读取分配返回值，不能把“通常观测到 0”当作通用保证。TMEM 地址不是普通的线性字节指针。

12.4 三套信息不要混淆

名称 用途
A_tmap/B_tmap TMA 如何从 global 取数据、怎样写入 SMEM
a_desc/b_desc MMA 如何定位 SMEM 中的输入
i_desc MMA 的类型、输出形状等指令属性

i_desc 在这里指定 A/B 为 BF16、累加为 FP32、M=128、N=256。源码分别通过 BLOCK_N/8 和 BLOCK_M/16 编码形状字段。函数名 tcgen05_mma_f16 中的 f16 对应指令 family，不代表输入被改为 IEEE FP16；实际 A/B 类型由 descriptor 指定为 BF16。

13. 每轮 TMA、barrier 字节计数与等待

最外层 iter_k 遍历 K/BLOCK_K 轮。对于 K=4096，共 16 轮。

2D 分支每轮对 A 发四次 TMA、对 B 发四次。循环里的 k 是 TMA 切片号，作用对应 MMA 阶段的 k1，但不是同一个循环：

3D 分支一次搬 A、一次搬 B，第三维坐标为 off_k/64。因为第三维表示 64 元素切片，所以它使用切片编号而不是原始 K 元素编号。

两种分支搬运的总字节数相同，barrier 的 expect_tx 都是 196608B。TMA 完成通知会抵扣待完成字节数；arrival 与字节完成条件均满足后，该 barrier 阶段完成。

线程通过 acquire 语义的 mbarrier_wait() 等待，确保随后消费的是已完成的搬运结果。之后的 tcgen05.fence::after_thread_sync 用于连接线程同步与 tcgen05 操作的顺序要求。fence 不代替完成等待，不能删除 wait 后仅保留 fence。

14. 发起 MMA：描述符、首次不累加、commit

14.1 make_desc() 做什么

它将起点地址、SBO、格式固定位和 swizzle 模式编码成 64 位值。desc_encode() 将相应字节地址/偏移按 16B 单位编码，低 4 位因对齐而省略。

v2 中的设置 含义
desc_encode(addr) 本次 MMA 的输入起点
desc_encode(8*128) 放入 SBO 字段 下一组 8 行相隔 1024B
1ULL << 46ULL 按 descriptor 格式设置固定位
2ULL << 61ULL 128B swizzle

描述符的格式固定位不是某个“开启 Tensor Core 优化”的开关。LBO 在本例 K-major swizzled 模式下不用编码，详见第 7 节。

14.2 为什么第一条 MMA 单独写

tcgen05_mma_f16() 最后一个参数转换为“是否非零”的谓词：

整个 K 归约的第一条 MMA 不应读取旧 TMEM 值，所以第一轮第一条传 0。其余指令继续累加。

源码把每轮第一条的最后参数写成 iter_k：第一轮为 0，后续轮为非零。**不是乘以 iter_k，也不是选择第 iter_k 块 TMEM。**其余指令都传 1。

14.3 源码循环数没有少

源码先手动发出 (k1=0,k2=0)，再处理 k2=1、2、3；之后循环 k1=1、2、3，各发四次 MMA：

K=4096 时，每 block 有 16 轮 iter_k，总计 256 条 MMA。最终都累加到同一块输出 tile。

14.4 commit 与等待各自负责什么

MMA 是异步的。tcgen05.commit...mbarrier 安排在前面的 MMA 完成后向 barrier 发完成通知，它本身不阻塞到计算结束。线程再执行 mbarrier_wait()，确认 MMA 已结束，才可以让下一轮 TMA 覆盖 A/B 的 SMEM。

15. v2 的时间线：还没有搬运/计算流水重叠

虽然 TMA/MMA 指令异步发起，v2 使用一份 A/B 缓冲，并在每阶段后等待，因此本轮数据流仍然串行。

顺序 等待的 parity 发生的事情
1 0 发 TMA，设置本轮 192 KiB 的完成字节数
2 0 等待 TMA 完成，随后翻转 phase
3 1 发 16 次 MMA，commit 完成通知
4 1 等待 MMA 完成，随后再次翻转 phase
5 0 下一轮 TMA 可以覆盖同一块 SMEM

phase 保存的是阶段奇偶性 0/1，不是“这个 barrier 只有两个完整阶段”。每次完成都会进入后续阶段，代码只需跟踪 parity。

实际顺序为 load0 → wait → MMA0 → wait → load1 → ...。后续 pipelining 才会引入多缓冲等机制，将下一轮数据搬运与当前计算重叠。不能把 v2 的性能变化全部解释成“已经有流水线”。

16. v1/v2 的 TMEM 输出布局与写回规则

输入 SMEM 布局变了，但本例的输出形状、TMEM Layout D 和 epilogue 没变。程序看到的是 128×256 个 FP32 累加结果。输入的 swizzle 不会自动施加到输出行列上。

16.1 TMEM 取数地址

源码每轮 n 从 0 遍历到 BLOCK_N/8-1，本例共 32 轮。地址由 taddr、warp 起始行和列起点组成：

高位表达行、低位表达列，不是普通 row×stride+col 的字节指针。指令 .32x32b.x8 在这里让 warp 的每个 lane 取得对应行的 8 个 FP32；lane 所对应的行由加载布局隐含确定，因此传入地址中不直接出现 lane_id。

tcgen05.wait::ld.sync.aligned 等待本次 TMEM load 完成，再使用寄存器中的结果。前面的 tcgen05.fence::after_thread_sync 建立所需顺序。PTX Layout D

16.2 BF16 转换与 global store

每个线程每轮取得 8 个 FP32，转换为 8 个 BF16，打包成 4 个 nv_bfloat162，共 16B。再通过一次 16B 向量 store 写到 C。

128 个线程各写一行；32 轮完成每行的 256 列。线程内部的 8 个元素连续，但相邻 lane 写到不同的行，因此这种跨 warp 访问仍然是跨行分散的，不能因使用 int4 就称为完全合并写入。

最后 __syncthreads() 确保所有线程完成 TMEM 读取，再由 warp 0 的全部线程协同释放 TMEM。TMEM 释放不能在其他 warp 还读数据时提前执行。

17. 固定源码中的笔误和适用边界

17.1 两处旧注释

  • 第 73 行写输入是 (MMA_M,8) 连续块，这是 v1 风格的旧注释。v2 的基础宽切片为 (H,64) BF16，并在其中应用 128B swizzle。
  • 第 137 行写最终 store 到 smem，但实际写入 C_ptr，目的地是 global memory。中间经过寄存器，没有把输出先写回 SMEM。

17.2 2D 分支 B 的 global height 应为 N

17.3 这是整除形状的教学 kernel

当前入口使用整数除法安排 grid 和 K 循环，输出没有尾部掩码，面向 M 是 128 的倍数、N 是 256 的倍数、K 是 256 的倍数的形状。TMA 的边界机制并不能自动补齐代码未调度的输出 tile 或被整除截断的 K 轮次。

它还要求支持相应 tcgen05 指令和资源规模的 GPU。不能仅根据产品属于“Blackwell”就假定任意设备都支持同一组指令和 192 KiB/block 的配置。

18. 六个常见疑问与对应答案

问题 答案 对应章节
3D 初始化为什么没传 swizzle？ 专用函数内部已固定配置 128B swizzle 5.1
box 最内维为什么从 8 变成 64？ BF16 每元素 2B，分别对应 16B 和 128B 的每行切片宽度 1、2、10
TMA load 为什么看不到 swizzle？ 模式在 tensor map 中，硬件搬运时执行 5.2
MMA 为什么看不到 XOR？ SMEM descriptor 包含模式，硬件按该布局取数 5.3、14
v1/v2 的 SMEM 和 TMEM 有何区别？ SMEM 切片宽度和地址变了；本例 TMEM 输出形状与取数布局没变 2、6、16
v2 为什么分 k1/k2，能否一层循环？ 分别表示宽切片和片内 MMA；可用 j/4、j%4 等价替换 8、9
元素公式中的 128 是什么？ H=128 是 A 的行数；另一处 128 是每行字节数，单位不同 6
LBO/SBO 为什么变化？ 输入布局变了；SBO 跨 8 行，v2 K-major swizzled 模式不使用 LBO 字段 7
k2*32 为什么不乘 BLOCK_M？ 只选择第一行的 descriptor 起点，其余行由布局描述符定位 8、9
MMA 是否把 SMEM 还原成普通数组？ 不做整块还原，按 swizzled 地址直接读取正确的逻辑元素 5.3
128B TMA 是否只搬 128B？ 128B 是切片行宽，单条指令可搬整个多行 box 2
第一条 MMA 传 iter_k 是乘数吗？ 只是零/非零的累加开关 14.2

19.4 这组结果能说明什么

  • 本地 v2a 相比 v1a：748/263≈2.84×；v2b 相比 v1b：764/264≈2.89×。从本地舍入延迟计算也得到相近结果。
