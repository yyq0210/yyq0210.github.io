Blackwell GEMM V4 图解：把搬运与计算拆成两个循环，读懂 7-stage 流水线和 15 个 barrier

V3 已经可以让下一块数据的 TMA 搬运与当前 MMA 计算重叠。V4 再进一步：用两个 warp 分别控制搬运与计算，让两个循环独立推进；只在数据没准备好、旧缓冲不能覆盖、最终结果尚未完成时等待。

理解 V4 最容易混淆的地方，不是矩阵乘公式，而是“发起”和“完成”的区别。代码走到了下一行，不代表异步引擎完成了上一项工作；控制线程退出循环，也不代表 TMEM 中的结果已经可以读取。

本文结合 gau-nernst 的 Warp specialization 博客章节 与实际源码，逐步解释线程分工、SMEM/TMEM 布局、stage 复用、barrier 和 phase，并加入本地 B300 的 V4 1271 TFLOPS 实测记录。

源码固定在提交 afcb20b1bd89065c31a1575c276aba686fc4dfce，与本次阅读的 main 版本内容一致。下文的行号都指这份快照。原文历史链接与当前仓库路径存在差异，本文以固定源码的默认参数为准。图解、数值推导和 CPU 调度模型独立整理；没有重新运行 GPU benchmark。

1. 先约定几个名称，避免把不同层次混为一谈

名称 本文含义
block / CTA 一组 128 个 CUDA 线程，负责一个输出 tile
输出 tile 当前 block 最终写入 C 的 128×128 区域
K tile / tile i 第 i 轮 K 方向数据，默认宽度 64
stage / buffer SMEM 中存放一份 A/B 输入的可复用槽位
L(i) 提交 tile i 的 A/B TMA 搬运；不是“已经搬完”
C(i) 提交 tile i 的 4 条 MMA 和对应 commit；不是“已经算完”
T[s] stage s 的 TMA 完成 barrier，供 MMA 端等待
D[s] stage s 的 MMA 完成 barrier，供 TMA 端等待
F 最终完成 barrier，也就是源码中的 mainloop barrier

这里的 D[s] 是完成通知的简称，不是输出矩阵 D。图中一个 C(i) 表示一组 MMA，而不是一条 MMA 指令。L(i)、C(i) 的下标是 tile 编号；T[s]、D[s] 的下标才是 stage 编号。

所有输入 A/B 均为 BF16，累加为 FP32，输出转为 BF16。物理输入形状是 A[M,K]、B[N,K]，计算的是 C=A×Bᵀ。

4. Block 变小，为什么反而配置更多 stage？

输出 tile 大小、K 分块宽度、stage 数，是三个不同的参数。

  • 输出 tile 决定 block 最终负责多少个 C 元素。
  • BLOCK_K 决定每轮沿 K 方向取多长的数据。
  • stage 数决定有多少个输入缓冲槽位可用于提前准备后续数据。

stage 增多不会扩大这个 block 的输出范围。所有 stage 都服务于同一个输出 tile 的 K 方向归约。

从空间上看，V4 每 stage 从 96 KiB 缩小到 32 KiB，才有空间放下 7 份。保持 V3 每 stage 96 KiB 而直接放 7 份，会需要 672 KiB A/B 空间，完全是另一种资源要求。

从调度上看，V4 单轮计算量为 V3 的四分之一：N 和 BLOCK_K 都减半。更深的缓冲可能帮助提前准备更多轮输入、减少供给不足，但这只是调优动机，不能据此证明 7 最优。更多 stage 也会增加 SMEM 占用，影响驻留与调度。

**小 block 并不必然需要 7 个 stage。7 是当前源码选定的配置。**其资源可行性、最佳深度和性能都需要结合目标 GPU 与实际形状测试。

6. 128B swizzle 与每轮四条 MMA

V4 沿用 V2/V3 的 3D tensor map 与 128B swizzle。A 的 globalDim 为 {64,M,K/64}，B 为 {64,N,K/64}；对应 globalStrides 为 {K×2,128} 字节。默认 boxDim 对 A/B 都是 {64,128,1}。

这里 tensor map 的 rank 仍为 3，但因为 BLOCK_K=64，box 第三维大小恰好是 1。第 i 轮 TMA 的第三维坐标是 i*64/64=i。

每份 A/B 是 128 行，每行 64 个 BF16，也就是 128B。行内分成 8 个 16B 包；每个包内部有 8 个 BF16。对行号 r、片内 K 坐标 q：

matrix_base 为当前 stage 的 A_smem 或 B_smem。各 stage 起点满足该布局的对齐条件。XOR 改变 16B 包的槽位，不改变包内部元素顺序；这个公式用于理解物理布局，代码不需要手动对 TMA/MMA 的每个元素再做一次 swizzle。

MMA descriptor 继续设置 SBO=8×128=1024B 和 128B swizzle 编码 2。默认 BLOCK_K=64，一轮只需四次 MMA：

片内 MMA 逻辑 K 范围 descriptor 起点相对 A/B 基址
0 [0,16) 0B
1 [16,32) 32B
2 [32,48) 64B
3 [48,64) 96B

这些是第一行的起点，其余行如何定位由 descriptor 的布局规则决定。不要把完整单元素 XOR 公式再套到已经声明 swizzle 的 descriptor 上。

源码仍保留通用 k1/k2 循环，但当前 BLOCK_K/64=1，从 k1=1 开始的外层循环不执行。实际执行的是首条 MMA，加 k2=1、2、3。

整个 K 归约仅第一条 MMA 禁止读取旧累加值。后续 stage 回到 0 时仍要继续累加，不能用 stage_id==0 作为输出清零条件。

7. Grid、warp 与线程：谁在做什么

每个 block 128 个线程，warp_id=tid/32。host 的 grid 大小是 (M/128)*(N/128)；kernel 将一维 block 编号映射回输出 tile 的 M/N 坐标。

操作 执行者
初始化全部 barrier warp 0 的 elected thread
TMEM alloc warp 1 全部 32 个线程
TMA 主循环 warp 0 的 elected thread
MMA 主循环与最终 commit warp 1 的 elected thread
等最终完成、读 TMEM、写输出 全部 128 个线程
TMEM dealloc warp 0 全部 32 个线程

所谓“专门的 TMA warp”，在这个 kernel 中是用该 warp 的一个 elected thread 提交指令，不是 32 个线程分别搬一部分 A/B。TMA 引擎实际完成搬运。

warp 2、3 不参与主循环发起，但参与最终输出。四个 warp 对应 TMEM 的四段行，因此不能简单删成两个 warp 后原样保留输出逻辑。

初始化后通过 fence.mbarrier_init.release.cluster 发布 barrier 初始化，再用 CTA 同步使各线程开始使用共享状态。TMEM alloc 返回的地址保存在共享 tmem_addr 中，后续读取这个返回值，不应把“本例通常得到 0”当成通用硬编码规则。

9. V4 的改变：两个独立循环，等待随数据依赖移动

源码第 139–153 行把主循环放进不同 warp 的分支。以下为保留同步含义的伪代码，不是可直接编译的 CUDA：

V4 的 compute 内没有每轮末尾的 MMA wait。C0 提交后，如果 tile 1 的 TMA 已经完成，就可以继续提交 C1。所有计算由同一个 MMA 线程按 K 顺序提交到同一个 TMEM 累加器，仍保留该计算序列需要的累加依赖；“提前提交”不表示允许重新排列 K tile 或由多个独立线程随意更新同一累加器。

与此同时，TMA 端只能覆盖已经释放的槽位。两个循环无需在每轮结束时汇合，由各 stage 的通知建立生产/消费关系。

10. Barrier 数量：V3 是 3 个，V4 是 15 个

对这两个具体实现，设 stage 数为 S：

用途 V3 V4
当前输入搬好：TMA barrier S S
旧计算完成：MMA barrier 1 S
整个计算完成：独立 mainloop barrier 0 1
合计 S+1 2S+1

V3 默认 S=2，因此 3 个；V4 默认 S=7，因此 15 个。15 不是所有 warp-specialized kernel 的固定数量，而是这份源码协议的结果。

源码用一个连续的 64-bit 数组分区：

名称 报告完成的来源 等待者 检查的问题
T[s] 对该槽位的 A/B TMA 完成通知 MMA 控制线程 当前输入能读了吗？
D[s] MMA 计算完成后由 commit 安排的 arrival TMA 控制线程 旧输入能覆盖了吗？
F 主循环最后的额外 commit 全部输出线程 全部计算完成了吗？

每个 barrier 初始化 arrival count=1。需要 arrival 的是通知协议中的一个发起者，不是等待线程总数，所以 F 有 128 个等待者也不需要将 arrival count 设置为 128。

V3 每轮等完当前 MMA 才复用唯一的 MMA barrier；V4 的搬运端要独立查询不同槽位，因此给每个槽位一个 D[s]。

T 与 D 不是 15 道依次通过的关卡。前 14 个构成 7 对重复使用的通知通道，F 只在收尾使用。

各槽位分别形成以下链：

槽位 第一轮 第二轮 第三轮
0 L0 → T0 → C0 → D0 L7 → T0 → C7 → D0 L14 → T0 → C14 → D0
1 L1 → T1 → C1 → D1 L8 → T1 → C8 → D1 L15 → T1 → C15 → D1
2 L2 → T2 → C2 → D2 L9 → T2 → C9 → D2 L16 → T2 → C16 → D2
3 L3 → T3 → C3 → D3 L10 → T3 → C10 → D3 L17 → T3 → C17 → D3
4 L4 → T4 → C4 → D4 L11 → T4 → C11 → D4 L18 → T4 → C18 → D4
5 L5 → T5 → C5 → D5 L12 → T5 → C12 → D5 L19 → T5 → C19 → D5
6 L6 → T6 → C6 → D6 L13 → T6 → C13 → D6 L20 → T6 → C20 → D6

箭头经过 T/D 时表示相应完成条件已经满足。相同 barrier 在不同列中使用不同代数，不能把第二轮的 T0 当成第一轮留下的旧通知。

一种合法的交错是：

  1. TMA 端开始提交 L0、L1 等；不需要等待全部七个输入搬完。
  2. L0 完成后，MMA 端提交 C0。
  3. L1 完成后，MMA 端可以在 C0 仍未完成时提交 C1。
  4. TMA 端提交到 L6 后，尝试 L7 时检查 D0。
  5. C0 完成、D0 就绪后，可以搬入 L7，即使 C1 等后续计算还没完成。
  6. TMA 端尝试 L8 时再检查 D1；MMA 端按序继续消费。

这是依赖关系示意，实际交错由硬件进度决定。代码没有“必须先发完七次 load 才开始 compute”的全局阶段划分；多个 stage 也不保证恰好七个传输同时占用 TMA 引擎。

15. 两个 warp 的 phase 不共享，为什么还都只用一个标量

源码的 int phase=0 是线程局部变量。TMA elected thread 与 MMA elected thread 分别维护自己的 phase，各自的 lambda 引用捕获也只引用本线程的局部对象。

两个循环都从 tile 0 开始顺序访问 stage 0…6。每绕完一圈就翻转，所以在各自处理 tile i、执行本次 wait 之前：

它们可能在不同时间到达同一代，更不需要实时相等。一个标量足够，是因为每个线程自己的访问顺序固定，可以从 tile 编号推导每个 stage 的代数。

MMA 端等当前 TMA 一代，用 phase；TMA 端为了覆盖槽位，等上一代 MMA，用 phase^1：

tile i stage 本线程当前 phase TMA 端等 D 的 parity MMA 端等 T 的 parity
0…6 0…6 0 1，初始空槽检查 0，第一代输入
7…13 0…6 1 0，等 C0…C6 1，第二代输入
14…20 0…6 0 1，等 C7…C13 0，第三代输入

更新局部变量不是用软件修改硬件 barrier。硬件在满足该 phase 的 arrival 和 transaction 完成条件后自行推进阶段。局部 phase 只给本次 wait 提供期望参数。

初始化时 barrier 处于 phase 0。搬运端使用相反 parity 1，使初始空槽位的检查直接通过；这是流水线的启动安排，不是已经真的执行过一次 MMA。若第一圈也等待 MMA phase 0，就会出现“没有搬运就不能计算，没有计算又不能搬运”的循环等待。

之后的正确性依赖逐槽位交接，不能只拿一个 0/1 变量就随意查询跨越多代的状态。若改成乱序消费或独立复用部分槽位，原来的单标量推导未必适用。

也可以用更明确的两个名字表达同样的协议：TMA 线程的 release_wait_phase 从 1 开始，MMA 线程的 ready_wait_phase 从 0 开始，分别绕圈翻转。源码使用 phase 和 phase^1，表达的是同一个相位差。

V3 的最后一轮仍然执行 MMA wait：

因为前面每轮也都等完，V3 不需要独立 F。

V4 的 MMA 线程最后只是发完了所有计算。它退出循环、所有线程通过 __syncthreads()，仍不能保证异步计算完成。因此源码在 MMA 循环后额外 commit 到 F，再让所有输出线程等待 F 的 phase 0。

这次 final commit 不会额外计算一次矩阵乘，也不会清空累加器；它增加的是完成通知。F 只使用一次，因此不需要循环翻转 parity。

**必须有正确的最终完成等待，但独立 F 不是唯一选择。**也可以正确定位并等待最后一轮计算的完成通知，或采用其他满足顺序要求的协议；源码增加 F 是为了让收尾不必再计算最后一个 stage 和对应 parity。

尤其是最后一批缓冲，不会再有下一次 load 复用它们。不能指望 load 内的 D 等待替输出线程等完最后的计算。

17. K=256 只有四个 tile，为什么源码还分配七个 stage

全局 K 和 BLOCK_K 要分开：全局 K 是整个归约长度，BLOCK_K 是每轮长度，stage 是槽位数量。

实际只调用 L0…L3 和 C0…C3，用 stage 0…3。stage 4…6 没被访问，但仍占分配空间，相关 barrier 也仍被初始化。

配置 A/B 动态 SMEM K=256 的使用情况
S=7 224 KiB 4 个槽位各用一次，3 个未使用
S=4 128 KiB 4 个槽位各用一次
S=3 96 KiB stage 0 在旧计算完成后复用一次
S=2 64 KiB stage 0 存 tile 0/2，stage 1 存 tile 1/3

这些选择表达同一个数学计算，但性能不必相同。7 不是 K=256 的必要配置；4 也不是唯一正确配置。

当前 V4 两个循环都直接遍历 num_iters，没有 V3 那种无条件预取 S−1 次的边界问题，因此正的 tile 数少于 S 时，未使用槽位可以保持空闲。这里仍要求完整 K tile；K=0 或非整除尾部不能借此当作已处理。

K=256、S=7 时没有缓冲覆盖，但还是必须等待最后的 C3 完成后才读 TMEM。当前实现仍使用 F。若改 S=4，F 为 mbars[8]，barrier 总数变为 9；不能只改数据区大小而保留不一致的 barrier 地址计算。

18. K=4096 的实际循环与收尾

默认 BLOCK_K=64，所以 num_iters=64。两个控制循环各处理 tile 0…63，TMA 共提交 128 条 A/B 搬运指令，每个 block 的 MMA 数为 64×4=256。

stage 0 用于 tile 0、7、14、21、28、35、42、49、56、63，共十代；stage 1…6 各使用九代。阶段使用次数不必完全相等，最后一圈可以是不完整的一圈。

最后 tile 63 使用 stage 0，等待 T0 的 parity 是 (63/7)%2=1。但采用独立 F 后，输出代码不用依赖这个推导，始终只等 F 的 phase 0。

最终输出沿用前面的 TMEM Layout D：warp 0/1/2/3 分别读取 tile 行 0–31、32–63、64–95、96–127。每线程每次读 8 个 FP32，等 tcgen05.wait::ld 后转为 8 个 BF16，用 16B store 写 global C；N tile 宽 128，因此每线程循环 16 次。

每线程负责的 global 行是 off_m+tid，列为 off_n+n*8。线程内部的 8 个元素连续，不代表相邻 lane 的写入也是相邻的 16B；相邻线程写的是不同输出行。

所有线程读完 TMEM 后再做 CTA 同步，由 warp 0 协同 dealloc。源码第 161 行“store to smem”的旧注释与实际代码不符，实际输出写入 C_ptr 指向的 global memory。

19. 把所有同步操作放在一张表里

操作 建立的条件 不能代替什么
barrier init + init fence 初始化并发布 barrier 状态 不能表示数据已搬好
TMA 发起 提交 A/B 搬运 不能表示已经搬完
arrive.expect_tx 登记 arrival 与预期完成字节数 不是等完成
wait(T[s], phase) 当前输入搬运已完成 不能保证旧输出归约全部完成
tcgen05 MMA 发起 提交矩阵乘 不能表示 TMEM 立即可读
commit 到 D[s] 安排前面 MMA 完成后的槽位通知 不是在这里阻塞等完
wait(D[s], previous_phase) 允许覆盖该槽位的旧输入 不负责所有输出线程的最后等待
commit 到 F + wait(F,0) 确认整个提交序列完成 不替代最后的 TMEM load wait
tcgen05 fence after_thread_sync 建立线程同步后 tcgen05 操作的顺序要求 不是独立的完成通知
__syncthreads CTA 线程汇合与相应共享访问同步 不会自动等完异步 MMA
tcgen05.wait::ld 等 TMEM→寄存器读取完成 不等价于整个 mainloop 同步

TMA 数据就绪、输入槽位释放、最终输出就绪，是三个不同的依赖。它们不能用“反正有一个同步”来互相替代。相关原始语义参见 PTX mbarrier 和 tcgen05 memory consistency。

20. 性能：B300 的 V3 1039 → V4 1271 TFLOPS

本次提供的比较数据如下，B200 列按用户表中的整数保留：

kernel B200 教程 TFLOPS，取整 B300 本地 TFLOPS
CuBLAS 1507 1676
V3 pipelining 940 1039
V4 warp specialization 1209 1271

教程原始数值分别为 1506.74、939.61、1208.83 TFLOPS。精确比例使用原始值，而不是由整数表反推。来源：博客 Warp specialization 性能表。

本次 CuBLAS 基线使用新提供的 1676，不沿用前篇的 1673。本次没有提供独立延迟实测，不将吞吐反算时间当作计时结果。相同工作量下，吞吐提升 22.3% 对应的时间减少约 18.3%，二者不能混称。

本地环境沿用前篇已确认的信息：NVIDIA B300 SXM6 AC、compute capability (10,3)、sm_103a 编译、PyTorch 2.13.0+cu129、torch.version.cuda=12.9、M=N=K=4096、BF16 输入。环境可见 8 张 GPU，不将本表理解为 8 卡聚合吞吐。本次没有重新确认完整计时脚本、驱动与时钟配置；教程使用 B200、PyTorch 2.9.1 + CUDA 13，跨设备差异不能全部归因于某一项硬件变化。

从源码可推导的优化机会包括：独立推进 TMA/MMA，减少每轮统一等待，对槽位逐一控制复用。但 V4 同时改变了 BLOCK_N、BLOCK_K、stage 数，整个版本的增益不能全部归因于“拆成两个 warp”。若要隔离因素，应固定其他参数再做实验或 profiling。

原始数据和来源见 benchmark.csv 与 environment.json。

21. 验证范围、源码导航与发布附件

配套 verify_pipeline.py 是 CPU 上的异步事件调度模型，区分 load 提交、load 完成、compute 提交、compute 完成、最终 commit、最终完成和输出读取。它通过多组 stage/tile 参数与随机合法交错，检查：

  • 旧计算未完成前不能覆盖槽位。
  • 输入未完成前不能提交对应计算。
  • 每个 tile 恰好搬运、计算一次，计算提交顺序保持不变。
  • phase 标量与每-stage 的代数一致，初始空槽可启动。
  • K=256、S=7 时仅使用前四个槽位。
  • F 只在所有计算完成后允许输出读取。
  • SMEM 地址、swizzle 双射、MMA K 分块和性能比例。

模型还构造两个错误情形：取消槽位释放等待会允许覆盖仍在使用的数据；只看“提交完”而不等最终完成，会允许过早读取输出。结果见 verification.json，示例交错见 schedule-default.csv 与 schedule-short-k.csv。

这个模型验证的是控制协议与算术，不模拟真实 CUDA warp 调度、编译器、内存可见性、引擎队列或 PTX 的完整语义，不替代 GPU correctness check 和性能测试。模型允许 TMA 完成出现不同顺序，并用有序 MMA 完成简化累加依赖；这不是对真实硬件完成顺序或时长的测量。

源码也不是任意形状通用实现：默认配置的 M/N 需要按 128 分块，K 需要按 64 分块；代码没有完整输出尾部掩码，也不应将 K=0 当作已支持。改变 stage 深度还需检查目标设备的共享内存上限与 launch 资源需求。
