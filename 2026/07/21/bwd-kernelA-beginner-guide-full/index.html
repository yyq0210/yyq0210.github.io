第 0 部分：Kernel A 是什么，在整个反向里处于什么位置

0.1 一句话定义

Kernel A = _flash_kda_bwd_dstate_scan（源码 L166-689），grid (N, H[, VSplit])。 它干一件事：沿时间反向，把"状态梯度" dS[D,D] 一个 chunk 一个 chunk 地往回传（D=128， 一个 chunk=CHUNK=16 个 token）。

打个比方：前向时状态 S 像滚雪球，从第 0 个 chunk 滚到最后一个，每个 chunk 都在它上面叠一层。 反向时要算"最终损失对每一层的敏感度"，就得倒着把这个雪球拆回去 —— 从最后一个 chunk 的 dS 出发，一步步推到第 0 个 chunk。这条倒着推的链就是 Kernel A 的串行扫描 （源码主循环 for (int t = t_tiles - 1; t >= 0; --t)，L288）。

0.2 为什么它是一块独立的 kernel（拆分背景）

反向原本有个巨大的融合 kernel _flash_kda_bwd_recurrence，把两件逻辑上分开的事塞一起 （源码注释 L50-67 白纸黑字）：

  1. 串行部分：反向 scan，把 dS[D,D] 从后往前传（chunk 之间有依赖，天生串行）。
  2. 大规模并行部分：每个 tile 独立算一堆 per-token 梯度（dv/dbeta/dq/dk/dg…），它们唯一的 跨-chunk 输入就是"进入该 tile 时的 dS"。

拆分方案：Kernel A 只跑串行 scan，并且对每个 tile 把"进入时的 dS"快照存进一块 per-tile 缓冲（fp32，[H*total_tiles, D, D]）；Kernel B 再用一个 CTA/tile 完全并行地读这个快照 + 前向存的中间量，复现所有 per-token 梯度。用"多写一趟 dS 快照到显存"换"把并行部分彻底解耦、 各自打满占用率"。 本文只讲 Kernel A（串行 scan 那半）。

0.3 Kernel A 每个 tile 算什么：5 个 GEMM + 1 个 combine

每个 chunk（tile）里，Kernel A 做 5 个小矩阵乘（GEMM）加一个逐元素"粘合"（源码注释 L81-87）：

GEMM 公式 形状（TN，fp32 累加） 干什么
G1 dU = Mqk^T @ do M=C N=Dv K=C do 经注意力矩阵回传
G2 dU += kr @ dS M=C N=Dv K=D dS 在这里进来（唯一读入 dS 的 GEMM）
G3 dvcorr = INV^T @ dU M=C N=Dv K=C 解逆矩阵得 v 修正梯度
G4 T1 = qd^T @ do M=D N=Dv K=C 组装新 dS 的第一项
G5 T1 -= kd^T @ (beta·dvcorr) M=D N=Dv K=C 组装新 dS 的第二项
— dS = exp2(gT)·dS + T1（combine，bf16 存回） 逐元素 更新 dS，传给上一个 chunk

"TN"是什么：MMA 硬件约定 sC[M,N] = sA[M,K] @ sB[N,K]^T —— A 正着放、B 转置放、沿 K 收缩。 所以表里每个 GEMM 都要指明 M/N/K 三个维度各是谁。

combine 是链的关键（源码 L656-672）：dS_new = exp2(gT)·dS_old + T1。exp2(gT) 是这个 chunk 的 门控衰减（gate decay），gT 是每个 feature 一个值 → 对角缩放（每行 k 乘自己的 exp2(gT[k])）。 算完 dS_new 就是"传给上一个 chunk 的 dS"，写回 smem，下一轮循环（t-1）接着用。

0.4 c 轴旋转 —— 为什么需要"寄存器内转置 MOVM_T"

这是 Kernel A 最"绕"的一点，务必讲清。看 G1/G3：

  • G1 产出 dU，形状 [c, v]（M=c，行是 token c，列是状态列 v）。
  • G3 要用 dU，但它沿 c 收缩（INV^T @ dU，K=c）→ 需要 dU 的转置 [v, c] 当 B 操作数。

朴素做法：把 dU 写进 smem，再按转置读回来 —— 一来一回浪费（smem 往返 + 一个 barrier）。 硬件有条专门指令 SM75_U32x1_MOVM_T：直接在 32 个线程的寄存器内部把一个小矩阵块转置， 不碰 smem。于是（源码 L590-599）：dU 累加器（本就在寄存器）→ cast bf16 → MOVM_T 转置 → 直接当 G3 的 B 操作数。G3→G5 之间的 bdv（=−beta·dvcorr）也用第二次 MOVM_T（L624-632）转置留在 寄存器。这就是注释里反复出现的 “c 轴旋转 / MOVM_T 寄存器内转置”，源自前向 K2 的 u_acc 惯用法。

MOVM_T 到底是什么（小白版）：ldmatrix/stmatrix 那一族里，有个变体能把一个 warp 寄存器里 持有的 8×8 bf16 小块"就地转置"—— 输入是"每线程持有矩阵的某几个元素"的 fragment 布局，输出是 转置后的 fragment 布局，全程在寄存器。省掉"写 smem→同步→按转置读回"整套动作。

基线 ncu（日志 §0）：

第 1 部分：第一场硬仗 —— 消灭 T1_smem，占用率 12.5%→50%（阶段 1-2）

整个 Kernel A 优化史分两大战役：先靠"寄存器融合"打赢占用率（阶段 1-2，本部分），再靠 "swizzle/padding"打赢 bank conflict（阶段 3-11，第 2 部分）。这个顺序不是随意的 —— 先修占用率 （让 SM 上住满 warp），bank conflict 才会浮出水面成为新瓶颈；反过来先修 conflict，会被低占用率 的延迟盖住看不出收益。

1.1 病根：fp32 中间缓冲吃光了 smem

基线的 5 个 GEMM 是"cooperative_gemm"（cute 提供的、整个 block 协作的 GEMM）。它们把中间结果 dU、dvcorr、T1 全都写进 fp32 的 smem 缓冲再读回来。其中最大的一块是 T1_smem（D×Dv fp32 = VSplit=1 时 128×128×4 = 64KB）—— 日志称之为**“大象”**。 124.48KB 的 smem 里，光这头大象就占一半，直接把"能不能塞下第 2 个 block"给否了。

1.2 先讲透两件事：大象是怎么来的、又是怎么被干掉的（零 cute 术语版）

小白最容易卡在这两句话：“干掉大象 T1_smem” 和 “每个 warp 无内部同步、无跨 warp 共享”。 下面用完全不带 cute 的大白话，从"一群人砌墙"的比喻讲清楚。

(a) 一个矩阵乘有两种分工方式

Kernel A 每个 tile 要算 5 个矩阵乘。一个矩阵乘 = 算一块输出矩阵 C = A×B。 一个 block 有 256 个线程（8 个 warp，每 warp 32 线程）。这 256 人算一块 C，有两种分工：

  • 方式一：全员合砌一面墙（旧代码，“cooperative_gemm”）。 256 个人一起砌同一面大墙（同一块输出 C）。既然大家都往同一面墙上贴砖，这面墙就必须放在 所有人都够得着的公共场地 = shared memory（smem）。T1 这块输出是 [128, 128] 的 fp32 矩阵 = 128×128×4 字节 = 64KB。这 64KB 就是那头大象 T1_smem —— 它之所以在 smem， 纯粹是因为"全员合砌一面墙，墙必须放公共场地"。

  • 方式二：把墙切成 8 段，一人一段（新代码，“每 warp 一个 MMA”）。 把这面 128 列宽的大墙，按列切成 8 段、每段 16 列，8 个 warp 一人包一段：

    warp0 只砌第 0–15 列，warp1 只砌第 16–31 列……各砌各的、互不重叠。 既然每个 warp 只砌自己 那一小段（16 列 × 128 行的一条），这一小段的中间结果小到能全部塞进这 32 个线程自己的口袋 （寄存器）里，根本不用放到公共场地 smem。→ 大象没了。

    【图 1】旧"全员合砌一面墙" vs 新"一人一段"

(b) 为什么"寄存器"就等于"省 smem、升占用率"

  • smem 是每个 SM 一池固定的公共场地（~228KB），住在这个 SM 上的所有 block 共用。 一个 block 占的 smem 越大，这个 SM 能同时住的 block 就越少 → 活跃 warp 越少 → 一个 warp 卡住时没别人顶上 → SM 空转。

  • 寄存器是每个线程自己的口袋，不占 smem 那池公共场地。只要口袋没爆（本例 64 寄存器/线程，0 spill）， 把中间结果放寄存器就等于凭空省下那 64KB smem。

  • 账一算：smem/block 从 124KB 掉到 50KB → 一个 SM 能住的 block 从 1 个变 4 个（228÷50≈4）→ 活跃 warp ×4 → 占用率 12.5%→50%。这就是 −37% 的来源:不是算得更快,是 SM 不空转了。

    【图 3】一个 SM 的 smem 池（~228KB）能住几个 block

© 为什么"切成 8 段"顺便消掉了几乎所有 __syncthreads

先说 __syncthreads 是什么：它是一道"全体 256 线程都到齐才能继续"的栅栏。什么时候必须用它? 当线程 A 往 smem 写了个东西、线程 B 要读它时 —— B 必须等 A 写完,否则读到旧值。栅栏很贵: 快的线程要干等慢的线程到齐。

  • 旧代码(全员合砌一面墙)为什么栅栏多:5 个矩阵乘是接力的(G1 的产出 dU 喂给 G2,G2 喂 G3……)。 每次接力都要经过公共场地 smem:G1 全员把 dU 写进 smem → 一道栅栏(等所有人写完)→ G2 全员从 smem 读 dU。每一次"经 smem 交接"就是一道栅栏,一条链下来 ~8 道。

  • 新代码(一人一段)为什么不用栅栏:warp0 从头到尾(G1→G2→G3→G4→G5→combine)只在自己那 16 列上 折腾,全程在自己口袋(寄存器)里接力。它读的旧 dS 是自己那 16 列、写的新 dS 也是自己那 16 列, 从不去读 warp1、warp2 产出的任何东西。既然 warp 之间没有"你写我读"的交接,自然谁也不用等谁 → 中间一道栅栏都不需要。这就是"无跨 warp 共享 → 无内部 __syncthreads"。

(c-2) 关键:为什么偏偏能"按列切"?——被切的那根轴不能被求和

有人会问:那我按行切成 8 段行不行?不行。 但准确的原因不是"列可以、行不可以"这条通用规律, 而是这条特定的链里,v 列轴从头到尾都没被"求和"掉,而 k 行轴在 G2 被求和掉了。先分清两种轴:

  • 自由轴(free):直接落到输出上、不参与求和。比如 C[c,v] = A[c,k] @ B[k,v] 里的 c 和 v。
  • 收缩轴(contract):被 Σ 求和掉、不出现在输出里。上面的 k。

规律:切一根自由轴 → 各段天然独立、最后拼接即可;切一根收缩轴 → 每段都要读别人的数据来求和 → 必须跨 warp 共享 + 栅栏。 dS/T1 的形状是 [D_k 行, D_v 列],我们切的是 v 列。逐 GEMM 看两根轴的角色:

步骤 运算 v 轴(列) k 轴(行)
G1 dU = Mqk^T @ do 自由(do 的 v 直落) —
G2 dU += kr @ dS 自由 收缩(dS 的 k 被 Σ 掉)
G3 dvcorr = INV^T @ dU 自由 —
G4 T1 = qd^T @ do 自由 自由(输出行)
G5 T1 -= kd^T @ bdv 自由 自由(输出行)
combine dS = exp2(gT)·dS + T1 自由(逐元素) 自由(逐元素)

看最右那列 v:从 G1 到 combine 全是"自由",一次都没被求和。 所以 warp0 只要拿 do、dS、bdv 的 第 0–15 列,就能独立算出输出的第 0–15 列,谁也不用问 → 列切成立、最后拼接。而 k 行轴在 G2 被整根 求和(dU[c,v] = Σ_k kr[c,k]·dS[k,v]):若按行切,warp0 只有 dS 的 0–15 行,算 G2 却要 dS 全 128 行 求和 → 必须去读别的 warp 的行 → 跨 warp 共享 + 落 smem + 加栅栏,独立性就没了。

【图 4】按列切(v,成立) vs 按行切(k,G2 就崩)

一句话:是"被切的轴在链里是否被收缩"决定的,不是"列/行"这个名字。 若链里哪一步出现了 Σ_v (对 v 求和),那即使按列切也照样要跨 warp 归约。本链恰好 v 全程自由、k 在 G2 收缩 → 只能沿 v(列)切。

1.3 具体怎么搬(照抄前向 K2 的惯用法)

关键洞察（日志 §0 策略）：前向 K2 根本没有 D×D 的 fp32 累加器 —— 它的状态更新全程是 “寄存器 MMA + STSM 写 swizzled bf16 smem”。把这套惯用法搬到 Kernel A，就能把 dU/dvcorr/bdv/T1 全部留在寄存器，fp32 中间缓冲一个不剩。

阶段 1（日志 §1）：先把 C×Dv 链（G1→G2→dU→G3→dvcorr→bdv）搬进寄存器。做法：

  • 用单 warp MMA 惯用法（MMA_Atom<SM80_16x8x16_F32BF16BF16F32_TN> + Tile<16,16,16>）， 每个 warp 拥有一个 16 宽的 v-block vb = warp_id（源码 L516-520 现在的形态）。
  • dU 在寄存器累加（G1 Mqk^T@do，再 G2 循环 kr@dS），cast bf16，MOVM_T 转置成 B 操作数， G3 INV^T@dU 在寄存器，beta·dvcorr 也在寄存器算完。
  • 消除：dU_smem/dvcorr_smem（fp32）、dU_bf 暂存循环、3 个 __syncthreads。
  • 本阶段 G4/G5 仍用 cooperative_gemm（大象 T1 留到阶段 2 处理）。
  • 结果：−6.7% / −6.9% / −11.9%。gradcheck L0 PASS，cos 0.99993，0 spill。

阶段 2（日志 §2，大赢）：把寄存器链延伸到 D×Dv 链（G4/G5/combine），干掉大象。看现在的源码 L634-673 —— 每个 m-block 里：

  • G4 T1 = qd^T @ do、G5 T1 -= kd^T @ bdv 都是寄存器 MMA（T1_acc 是 MMA 累加器，在寄存器）。
  • combine dS = exp2(gT)·dS_old + T1 在寄存器完成：LDSM 读旧 dS 入 fragment（L658），与寄存器 T1_acc 融合（L661-669，gk0/gk1 是 gT 按 M-row 分的对角缩放），STSM 写回（L672）。T1 全程不落 smem。
  • G5 的减号靠预取负 beta 实现：b = -beta（源码 L614-615 -beta_smem[...]），让寄存器 gemm（C += A@B）自然得到 T1 = qd@do − kd@(beta·dvcorr)。

为什么每个 warp 能无内部同步地跑完整条链：见上面 §1.2© 的"一人一段"解释 —— 每个 warp 独占 它那 16 宽的 v 列，G2 只读 dS[vb,·]、combine 只写 dS[vb,·]，warp 之间不共享数据 → 中间零 __syncthreads，只在循环末尾一道 barrier（源码 L676）把整块 dS 发布给下一个 tile。

  • 消除的 smem：dU_smem/dvcorr_smem/T1_smem（fp32）+ dU_bf/bdv_bf（bf16），全没了。
  • 新 smem = dS[D·Dv] bf16 + (D+CHUNK+…) fp32 + 几块 bf16 MMA 操作数。启动器 KDA_LAUNCH_K2A 的 smem_ 公式相应删掉 fp32 里的 CHUNK·Dv + D·Dv 两项。

第 2 部分：第二场硬仗 —— swizzle 消灭 bank conflict（阶段 3a-3d）

占用率修好后，L1/TEX 吞吐钉在 96.69% = smem 访存管线打满。病根是 bank conflict：MMA 要按 "fragment 布局"从 smem 读小矩阵块，但 smem 若朴素行主序摆放，这种读法会撞 bank，硬件排队。 本部分的主线：用 swizzle 布局让每个操作数的 ldmatrix 读无冲突。

2.1 先失败一次：普通布局的 LDSM（阶段 3a）

阶段 2 的 ncu 假设：转置视图上的通用标量 copy 无法向量化 → 每个 16×16 tile 约 8 次窄 LDS → MIO throttle。ncu 直接建议用 ldmatrix（更少更宽的载入）。于是阶段 3a 把全部 6 个操作数载入 换成 ldmatrix tiled-copy（源码现在 L539-552 那套 make_tiled_copy_A/B/C 机器）。

证明了一件事：LDSM_T 在普通、非 swizzled 的 MN-major 视图上就能用，gradcheck bit 一致 —— 正确性不需要 swizzle。但结果只有 −1.5% / −1.2% / −2.6%，不理想。

ncu 揭示原因（日志 §3）：Warp Cycles/Issued 从 32 涨到 46（更差！），两个首要 stall Short Scoreboard 40.3% + MIO Throttle 32.1% = 72% 全是 smem-pipe。结论：kernel 不是受指令 数量限制，而是 shared-memory bank conflict 受限。 普通布局的 ldmatrix 砍了指令数，但 bank 冲突（例如 sQd 各行相隔 256B → 别名到同一组 bank → ldmatrix.trans 串行化）让 L1/TEX 仍钉死 97.5%。

👶 逐句拆开这段 ncu 诊断（小白版）

① Warp Cycles/Issued 32→46(更差)。 这个指标 = 平均每发射一条指令、一个 warp 要耗多少周期, 越大越堵(warp 越多时间在干等而非干活)。换 ldmatrix 后指令总数是砍了,但每条更慢 → 净负 → 直接推翻"减少指令数就会快"的假设。

② 两个首要 stall = 72% 全在 smem 管线。 ncu 会告诉你 warp 卡住时在等什么:

  • Short Scoreboard 40.3% = 在等一个短延迟片上访问的结果回来 —— 几乎总是 smem 读(scoreboard 记分板追踪"数据到了没",卡这儿 = 在等 smem 取数)。
  • MIO Throttle 32.1% = MIO 是所有 smem 指令(LDS/LDSM/STS)走的管线,Throttle = 管线已排满,新的 smem 指令发不进去、只能等。
  • 两者合 72% 全是 smem 相关 → 病根是 smem bank conflict,不是指令条数、不是算力。所以砍指令治不了病。

③ 机制:“sQd 各行相隔 256B → 别名到同一组 bank → ldmatrix.trans 串行化”。 拆三段:

  • 各行相隔 256B:sQd 是普通 [D,C] bf16,一行 128 个 bf16 = 128×2 = 256 字节 → 相邻行起点每隔 256B。
  • 别名到同一组 bank:bank 一圈 = 32 bank × 4 字节 = 128 字节。256B = 正好 2 整圈(256/128=2) → 隔整数圈 = 回到完全相同的 bank。于是不同行的对应元素 bank 号一模一样 = “别名(alias)”:不同行却映射 到同一组 bank。ldmatrix 要跨多行取一个 8×8 小块,这些行 bank 全重合 → 挤同几个 bank → 冲突。
  • ldmatrix.trans 串行化:带转置的 ldmatrix 本该一条指令并行搬一个小块进寄存器,但 bank 全重合 → 硬件无法一拍完成 → 只能一组 bank 一组 bank 地串行搬 = 串行化,一条并行指令被拉成好几拍。

④ “L1/TEX 仍钉死 97.5%”。 L1/TEX 是含 smem/MIO 的存取单元,97.5% = 它几乎全程在忙 —— 但不是在高效 搬数据,而是在反复串行处理 bank 冲突(忙于重试,不是干活)。所以换了 ldmatrix、砍了指令数,L1/TEX 因 bank 冲突照样钉死 97.5%、warp 全卡等 smem → 净负。这正是逼出下一步(s3b/3c 上 swizzle)的直接证据。

教训：ldmatrix 本身不解决 bank conflict —— 它只是把"很多窄 LDS"合成"一条宽 ldmatrix"。 如果那条宽 ldmatrix 读的 smem 布局仍撞 bank，照样串行化。必须配 swizzle 才有用。

2.2 分诊：只 swizzle "R1 产出"的操作数（阶段 3b-3c）

关键分诊（日志 §4）：不是所有操作数都能 swizzle。

  • R1 产出的操作数（qd/kd/kr）：由 R1 逐元素写进 smem → 写地址可自由重排 → swizzle 友好。
  • cp.async 载入的操作数（do/mqk/inv）：向量化 16B 载入会被 swizzle 打碎，且每 tile 只用一次 （1 次 LDSM → 冲突代价可忽略）→ 保持普通布局。

👶 "向量化 16B 载入会被 swizzle 打碎"是什么意思

先看两拨操作数进 smem 的方式完全不同:

  • qd/kd/kr 是 R1 在 kernel 里逐个元素算出来、逐个写进 smem 的 → 写到哪个地址完全自由。
  • do/mqk/inv 是用 cp.async 从显存整块搬进 smem 的 → 一次搬 16 字节 = 连续 8 个 bf16(硬件 向量化要求,搬运的最小单位就是"连续 16B",不可拆)。

swizzle 要做的事 = 打乱写入地址,让相邻元素散到不同 bank(即要求 8 个元素别再连续摆):

这两个要求直接打架:要把 8 个元素散开,就得把这一条 16B 拆成 8 次零散写 → cp.async 的"一次搬 16B" 向量化就没了,退化成慢速逐元素搬运。"被打碎"就是这个意思:swizzle 的散地址会把 16B 向量化拆成 8 次 小搬运,毁掉 cp.async 的性能。 而 qd/kd/kr 本就是逐元素写、没有"必须连续 16B"的包袱 → swizzle 随便加。

再补一刀"只用一次":就算不 swizzle、do/mqk/inv 保持普通布局会有点 bank 冲突,但它们每个 tile 只被 LDSM 读一次(用完即弃) → 一次读的冲突代价小到可忽略;而 qd/kd/kr 在 5 个 GEMM 里被反复读,冲突 被放大 → 值得 swizzle。结论:冲突代价小(只读 1 次)+ swizzle 代价大(打碎 cp.async)→ do/mqk/inv 保持 普通布局最划算。 这也正是后来 s7(硬去 swizzle 它们)回归、被回退的原因。

什么是 R1：Kernel A 不直接读前向存的 qd/kd/kr（那是 bf16、有精度损失），而是在片上用 fp32 重新算一遍（reconstruct）。源码 L407-493 就是 R1：从 raw q/k + gc + gT 重建 qd/kd/kr。因为是 逐元素现算，写到哪个 smem 地址完全自由 → 可以直接写进 swizzled 布局。

阶段 3b — swizzle qd/kd（源码 L118-120 QdKdSw = Layout_MN_INTER_Atom over [D,C]）： R1（生产者）写 sQd(col, r_row)，G4/G5（消费者）读同一个布局对象 → 由构造一致（无论 swizzle 怎么置换，写读同一对象就对得上，正确性与置换无关）。qd/kd 在 G4/G5 各用 8 次（8 个 m-block）→ 冲突代价大。

2.3 最后一个操作数：dS 的转置对偶 swizzle（阶段 3d）

dS 被两个正好互为转置的方向用（源码注释 L128-139）：

  • G2 读它当 B 操作数 [v,k]（源码 L529 DSb）；
  • combine 读/写它当 C 累加器 [k,v]（源码 L530 DSc）。

这跟前向 K2 的 State/TransposedState 完全同构。所以照抄它的**转置对偶（transpose-dual）**招：

  • DSb = Layout_K_INTER_Atom over [Dv,D]（B 操作数，LDSM_N，源码 L140-142）
  • DSc = Layout_MN_INTER_Atom over [D,Dv]（C 累加器，LDSM_T 读 / STSM_T 写，源码 L143-145）

妙处：K_INTER 和 MN_INTER 两个 atom 互为转置，tile_to_shape 一致铺贴 → DSb[v,k] 和 DSc[k,v] 命中同一个物理字节（源码注释 L134-136 说明：方形 VS1 和矩形 VS>1 都成立）。于是 dS 只存一份物理数据，两个方向都能无冲突读/写。全部 5 个 dS 站点（init/snapshot/G2-B/combine-C/ ds_out）都走这两个视图，一致性自动保证。cosize == D·Dv（INTER atom 无 padding）→ smem 不变。

👶 逐步拆开讲（小白版）

一块 swizzled smem 有"两端":写进去的生产者、读出来的消费者。

  • 消费者端(读):MMA 用 ldmatrix(LDSM)读它 —— s3~s5(swizzle 那几步)已经把这端配好,读 0 冲突。
  • 生产者端(写):R1 算出 qd/kd/kr 后,得先写进这块 swizzled smem —— 这端 s6 之前还没改。

病根:读端修好了,写端还在用"通用标量 copy"往 swizzled 地盘上写。 R1 phase-2 算完 qd/kd,原先用普通逐元素 copy(...)(一线程写几个元素)store 进 smem。但目标 smem 是 swizzled 布局,而普通 STS(scalar store) 对地址的摆法跟"swizzled 消费者读时的摆法"对不上 → 32 个 lane 的写地址挤进同一/少数几个 bank → 16-way STS 冲突(ncu op_st/store-conflict 一直高)。 即:读端(LDSM)已无冲突,写端(STS)还在拖后腿。

修法:把"写"也换成 stmatrix(STSM),让写和读用同一个 layout 对象。 STSM = stmatrix,是 ldmatrix 的孪生写指令。关键规则:swizzle 只有在"写和读用同一套 swizzle 变换" 时才无冲突 —— 读端 ldmatrix 带 swizzle,写端就必须用配套的 stmatrix(同一 swizzle)。所以 s6 把 R1 生产者 store 从"通用 copy"换成前向 K2 早就在用的 STSM 惯用法(源码 L485-491):

  • qd、kd 用 SM90_U16x8_STSM_T(带转置 _T —— 因为 qd/kd 后面要以转置形态喂 MMA);
  • kr 用 SM90_U32x4_STSM_N(不转置 _N)。

这样生产者写入用的 layout 对象和消费者读取用的 layout 对象是同一个 swizzled layout(同一个 CuTe layout 变量):写按它铺、读按它取 → bank 完美错开 → STS 冲突消失,qd/kd/kr 从"半吊子 swizzle (读好写差)"升级成真·stmatrix 通路(读写两端都 swizzle)。

为什么"正确性由构造保证"(免验证)。 swizzle 本质是打乱物理地址,但只要 store 和 load 引用同一个 layout 对象,"store 把元素 X 按打乱规则塞到某物理 bank"和"load 按同一规则去那个 bank 取 X"就是一个 置换 + 它的逆 —— 绕一圈,load 必然拿回原来的 X。swizzle 是对上层透明的地址重排,写读同源则数据语义 恒等。所以 s6 不改任何数值、只改物理摆放 → 无需重新验证正确性。

和 s11 的分工别搞混:s11 修的是 R1 输入 buffer q_sm/k_sm/gc_sm 的读冲突(pad stride); s6 修的是 R1 输出 buffer qd/kd/kr 的写冲突(STSM)。R1 一头(读输入)一尾(写输出),两处不同战场。

3.3 阶段 6/s8 —— cp.async 预取 R1 的 q/k/gc，碾碎 gmem long_scoreboard

  • Group B（inv/mqk/do）：GEMM 链消费 → 后 commit（L357），R1 之后 wait<0>（L496）→ 它的延迟 藏在"快照 + 整个 R1"后面。

第 4 部分：终局 —— 打破 bf16 的 4-way bank 地板（阶段 8-11）

这是全篇智力密度最高的一段。s9 后 ncu 说"还有 1.89B conf_ld"，但追这个数字的两次尝试 （s10 用更大 swizzle、s12-分析用 XOR-swizzle）都被证明是死路，真正的赢来自一个反直觉的 “奇数半-stride + 更小拷贝粒度”。

4.1 阶段 8/s10 —— ❌ dS INTER→SW32 真 xor-swizzle：回归，已回退

s9 ncu 确认 B32/B8 仍有 conf_ld ~1.89B。诊断：每个 INTER atom 都是 Swizzle<0,4,3> = 零个 xor 位 = 只交织、不分散 bank。真正分散 bank 的 atom 是 SW32/64/128（Swizzle<1/2/3,4,3>）。 s10 就把最大操作数 dS 从 K_INTER/MN_INTER 升级成 K_SW32/MN_SW32。

static_assert(cosize == D*Dv) 成立 → SW32 无 padding，smem 不变，占用率不是变量。gradcheck PASS → SW32 也是 transpose-coherent。正确性 OK，但性能全线回归 +11~12%，已回退。

为何输 —— 关键线索是 B1（+12.5%，和 B32/B8 一样）：B1 不受冲突限制（barrier/占用率受限）， 却同样严重回归 → 损失不是冲突权衡。SW32 给每次访问加了一个固定的额外 XOR 地址运算 （INTER 的 Swizzle<0> 会被编译器优化掉，SW32 不会），把热 GEMM 循环推过寄存器预算 → 4B spill。

教训（贯穿 s10 和后面的 s12-分析）：对我们的 16 宽 ldmatrix 子 tile，INTER 已经够了。 INTER 的"16B-run 交织"就足以让 ldmatrix.trans 触发；SW32 的额外分散在这里几乎买不到冲突缓解， 却在每次访问都花地址运算 + 寄存器 → 净亏。不要把操作数"升级"到 SW32/64/128。 1.89B 的 conf_ld 计数是真的，但不能靠更大的 swizzle atom 廉价移除（和 s7 是同类红鲱鱼）。

4.2 阶段 9/s11 —— 源码级归因：真正的冲突源不是 MMA 操作数

s10 死路逼出源码级重新归因：对 s9 跑 text-mode ncu（--page source），把 1.99B excessive shared wavefront 按 SASS 指令拆开（日志 §11）：

  • LDS.U16 = 1.24B (62%) = R1 对 q_sm/k_sm（bf16）的标量读，
  • LDS(32位) = 336M (17%) = R1 的 gc_sm（fp32），
  • LDGSTS(cp.async) = 214M (11%)，
  • LDSM/STSM（每个 MMA 操作数）= 0 冲突！

惊人结论：79% 的冲突是 R1 根本没被 swizzle 碰过 的 token-strided 标量读，而所有 ldmatrix 操作数 早已无冲突。 这正是为什么 s10（对 dS 的 LDSM 上 SW32）是纯代价 —— 它去追的那个操作数根本没冲突。

机制（日志 §11，务必看懂）：q_sm/k_sm/gc_sm 是 [C, D] row-major，行 stride = D = 128。 R1 读 q_sm[c*D + kp]：c（token）在 32 个 lane 间变化，kp（feature）在 fragment 槽内固定。 bf16 bank = ((c*128 + kp)/2) % 32 = (kp/2)%32 → 与 c 完全无关 → 32 个 token 全命中同一个 bank → 最坏 32-way 冲突。

修法（s11）：只 pad 这 3 个 R1 buffer 的行 stride —— 它们不是 MMA 操作数（qd/kd/kr 才是）， 所以 padding 对 GEMM 链不可见。QK_PAD = D+8 = 136（bf16）、GC_PAD = D+4 = 132（fp32）， 两者仍是 16B cp.async chunk 的倍数。

第 0 步 · 什么是 bank(存储体)。 shared memory 被切成 32 个 bank(编号 0~31),像 32 个收银窗口。 一个 warp 有 32 个 lane(线程)。黄金规则:一条读指令里,32 个 lane 若分别落到 32 个不同 bank → 一拍办完;若有 N 个 lane 挤进同一个 bank → 排队办 N 次 = N-way 冲突,慢 N 倍。bank 按地址算: 硬件按 4 字节一格编号,bank = (字节地址/4) % 32。一格 4 字节 = 2 个 bf16,所以对 bf16 元素: bank = (元素下标/2) % 32。

第 5 步 · 为什么 pad “对 GEMM 链不可见”(最易漏)。 MMA 的 ldmatrix 操作数吃的是 qd/kd/kr, 不是 q_sm/k_sm/gc_sm。后三者只是 R1 的临时输入 buffer,padding 只加在它们每行尾巴,R1 用 新 stride 136/132 索引即可,读到的有效数据一模一样,尾部废元素根本不读。所以 padding 停在 R1 内部, GEMM 看到的 qd/kd/kr 一个字节没变 → 零风险。这也顺带解释为什么 s10 是死路:它去给 dS(一个 ldmatrix 操作数)上 swizzle,而那个操作数本来就 0 冲突 → 追错了目标。

4.3 阶段 10/s12-分析 —— ⏭️ XOR-swizzle q/k：写代码前就被否决

显而易见的下一步 = XOR-swizzle q/k buffer。但它在动手前就被分析否决，因为可证明打不破 s11 的地板 （日志 §12）：

  • q/k 冲突是 token 变、feature 固定：32 lane 在同一 feature 读 32 个不同 token（行）。跨 token 的 bank 展开 = ((Δc)·STRIDE/2) % 32。完整 32-bank 分散需要 STRIDE/2 与 32 互质（奇数）， 即 STRIDE ≡ 2 (mod 4)。
  • 但 16B cp.async 写强制 STRIDE 是 8 的倍数 → STRIDE/2 是 4 的倍数 → 最多 8 个不同 bank = 4-way，硬地板。s11 pad 到 136：136/2=68 仍是 4 的倍数 → 卡在 4-way（这就是只买到 −19% 的原因）。
  • XOR-swizzle 受同一约束：cutlass 式 XOR 置换整个 16B（8×bf16）块，读地址两项都是 4 的倍数 → 仍 ≤8 bank = 4-way。XOR 无法分散到"16B-coalescing 粒度"以下。

绑定约束是 coalescing 单元，不是 swizzle atom（和 s10 同类死路）。只要还用 16B 写，bf16 的 token-strided 读就永远卡在 4-way。 想破地板，必须换更小的写粒度。

第 5 部分：split-V —— Kernel A 专属的并行度杠杆

前面每个 conflict 阶段 B1 都持平，因为 B1（B=1, N=1）并行度饥饿：grid = N×H = 128 个 block， 但 H20 有 78 个 SM 且每 SM 能住多块 → block 太少，SM 填不满。这跟 bank conflict 正交，swizzle 帮不上。

split-V（源码 L216-217、模板参数 VSplit） 是给 B1 补并行度的招：把状态的列轴 v 切给多个 CTA。 blockIdx.z = v_split 决定这个 CTA 负责哪 Dv = D/VSplit 列（源码 L189 constexpr int Dv = D/VSplit）。 所有按 v 索引的 buffer（dS/T1/dU/do）宽度变 Dv；只按收缩轴 k 索引的（mqk/inv/qd/kd/kr）保持全宽 D。 VSplit=1 时 Dv==D，所有布局塌回原始 monolithic 视图（bit-exact）。

  • 好处：grid 从 (N,H) 变 (N,H,VSplit) → block 数 ×VSplit → B1 从 128 block 变 256/512 → 填满 SM。
  • 代价：每个 v-band 的 CTA 都要重算一遍 R1（qd/kd/kr 是全宽、与 v 无关）→ VSplit 越大重复越多。
  • 基线时 split-V 自动派发：B1 大赢 −33%，饱和 grid（B32/B8）上中性（那里 block 本就够多）。
  • VSplit ∈ {1,2,4} 由 grid 占用率在 launcher 里自动决定（ctas_base = N*H < sm_count 时开大）。

小白记住：conflict 优化（swizzle/pad）修的是"每个 warp 跑多快"；split-V 修的是"有没有足够多 warp 填满 SM"。B32/B8 缺的是前者，B1 缺的是后者。 这就是为什么整个 conflict 战役 B1 一直持平 —— 它的病在别处（并行度），得用 split-V / grid remap 这类正交杠杆治。开放杠杆：VSplit>4 / grid remap。

第 6 部分：一句话教训总结（小白记这几条就够）

  1. 先修占用率，再修 conflict（第 1→2 部分）。占用率没修好时，bank conflict 被延迟盖住看不出； 反过来也一样。阶段 2 把 fp32 中间量搬进寄存器、干掉大象 T1_smem → 1→4 block/SM → −37%。

  2. swizzle 要读写成对、且只对"可自由重排写地址"的操作数做（第 2-3 部分）。R1 逐元素产出的 qd/kd/kr/dS 可以 swizzle（ldmatrix+stmatrix 成对）；cp.async 载入的 mqk/inv/do 要么保持普通、 要么把 swizzle 白嫖进 cp.async scatter（s9 plan-a），绝不加额外的生产者 pass（s7 plan-b 因此 +14.5%）。

  3. transpose-dual：一份字节喂两个方向（dS 的 DSb/DSc，第 2.3）。互为转置的 K_INTER/MN_INTER atom 命中同一物理字节 → 存一次、正读+转置读都无冲突、零 padding、smem 不变。

  4. INTER 对 16 宽子 tile 已够，别升级到 SW32/64/128（s10，第 4.1）。更大 swizzle atom 每次访问多花 XOR 地址运算 + 寄存器 → spill → 全线回归（连不受冲突限制的 B1 都退 = 铁证不是冲突权衡）。

  5. 别追不在关键路径上的 ncu 指标（s7 的 805M、s10/s12-分析的 1.89B conf_ld，第 3.2/4.1/4.3）。 先看"绑定 stall 是谁"。s7 时是 gmem long_scoreboard，追 shared conflict 白费；s8 crush 掉 gmem 后 short_scoreboard 才浮上来，那时 swizzle mqk/inv/do 才值得。

  6. 源码级归因胜过按 atom 瞎试（s11，第 4.2）。text-mode ncu 把冲突拆到 SASS 指令，发现 79% 冲突是 R1 没被 swizzle 碰过 的 token-strided 标量读（LDS.U16），所有 ldmatrix 操作数早已 0 冲突 —— 这才指向"pad R1 raw buffer"这个正确修法。

  7. bf16 token-strided 读的 4-way 地板由 16B-coalescing 锁死，破它必须换更小写粒度（s12，第 4.3-4.4）。 奇数半-stride 130（65 与 32 互质）+ 4B cp.async.ca → 读散满 32 bank。代价 4× LDGSTS 在延迟绑定的 B1 净赚（−4.2%），在富并行 B32/B8 大体抵消（−1%）—— 精算过的赌博，赢在最该赢的 B1。

  8. 构建陷阱（必记）：s* 都是被 bwd_launch.cu #include 的 header。改 header 不 touch csrc/smxx/bwd_launch.cu 就不重编，stale .so 给假结果。改任何 header 后必须 touch bwd_launch.cu 再 build。A/B 测试永远同 session、单变量（日志 §0 曾差点把变化误判成 caching-allocator 的抖动）。

  1. B1 并行度 —— VSplit>4（VS8 模板实例化 + 派发）/ grid remap；B1 仍 barrier/占用率受限（12.5%）。
  2. 计算侧 —— Compute SoL 现 64%；内存 stall 进一步下降后，GEMM 链本身成为下一个天花板。
