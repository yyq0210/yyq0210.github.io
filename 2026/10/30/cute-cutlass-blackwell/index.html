CuTe / CUTLASS Blackwell 图解：从 Layout 到 get_slice、partition 与 fragment

读 CuTe，先分清三个问题： 这是什么元素？它存在什么位置？谁用什么指令访问它？ 大部分看起来复杂的封装，都在把其中一种坐标换成另一种坐标。

UMMA 是 CUTLASS 中对 Blackwell tcgen05.mma 的称呼。本文围绕数据中心 Blackwell 的 Simple UMMA 示例展开，使用的是 SM100 接口；硬件指令、CuTe 布局与 C++ 封装会分层解释。

本文以 Colfax 的 Simple UMMA 讲解和 NVIDIA 的 01_mma_sm100.cu为主线。文中的精简代码均用于讲解，除明确标为可运行的例子外，不是完整可编译程序。图和地址例子是为解释代码重新推导的，不是硬件内部电路图。源码 main 会变化，本文按 2026-10-30 对照的版本解释。

主线例子（2×4 入门示意图除外）： M=512，N=1024，K=256；A/B 输入为 FP16，累加与 C/D 为 FP32；一个 CTA 128 线程；每轮输入 tile 为 128×256×64；每条 UMMA 为 128×256×16。单 CTA 的 cluster，不使用 TMA，不使用多阶段缓冲。

1. 九种视角，不是九份数据

图 1：改变视角通常只改变访问函数；跨存储空间要执行实际的 copy。

视角 它回答的问题 本例
数学 / 逻辑 矩阵中哪个元素？ A[m,k]；Acc[m,n]
GMEM 全局内存中哪个地址？ A_base + 2×(mK+k)
tile 哪个 CTA、哪轮 K、块内哪个位置？ CTA(0,0)，t=1，x=39
MMA 哪条矩阵指令、其内部哪个元素？ j=2，q=7
SMEM 数据写到共享内存哪个物理槽位？ swizzle 后的 byte offset
线程 / TV 哪个参与者的第几个值？ copy 阶段的 tid、value
TMEM 结果所在的专用行和列？ row=37，column=69
寄存器 哪条线程的哪个局部结果变量？ tid=37 的 rAcc[69]
物理实现 指令最终如何访问存储？ descriptor、tcgen05.mma、tcgen05.ld

最后一行中的“物理”指程序可见的地址与指令约定。CuTe 不暴露具体寄存器文件电路或 Tensor Core 内部乘加单元的接线。

地址布局 把矩阵坐标送到存储位置； TV 布局 把参与者和值编号送到逻辑元素； 运算布局 把问题分成硬件指令可执行的块。这三个函数可以组合，不能直接把它们的 stride 混在一起比较。

2. 从 Shape / Stride 开始读 TVLayout

Layout = Shape : Stride。Shape 给出每个坐标的取值范围；Stride 告诉你每增加 1，映射结果增加多少。一般的简单布局就是坐标与 stride 的内积。

这里行间有 padding，所以 size 不等于 cosize。一块内存需要多大的容量，要看能访问到的地址范围，而不只是数元素。

图 2：元素 (1,2) 同时拥有逻辑 id=5、内存偏移=8、线程 t=2 / 值 v=1，三者都正确。

小例子中，每条线程负责一列、两行，因此 TV(t,v)=v+2t。把结果解码回矩阵坐标，就得到 (m,n)=(v,t)。再送入上面的内存布局，才得到 6v+t。

CuTe 的逻辑线性编号通常以第一个 mode 为快维度。对 Shape(2,4)，编号是 m+2n；这并不表示数据必须按列存储。真实存储方向取决于你另行提供的 stride。

Tensor = Engine + Layout。Engine 可以是 GMEM 指针、SMEM 指针、TMEM 地址引擎、描述符迭代器，或者拥有局部存储的 ArrayEngine。因此， 看见 tensor / fragment，不能马上认定它里面是一组浮点寄存器。

_128 / Int<128>{} 表示编译期常数 128；运行时整数也可以参与 Shape/Stride。((128,16),1,4) 的顶层有三个 mode，第一个 mode 又有两个子坐标。它不是奇怪的五维物理内存，而是一棵坐标分组树。

3.5 为什么需要 partition，而不直接写下标？

简单例子可以手写两个数组下标。实际矩阵指令还包含 lane 分工、一个线程的多个不连续值、SMEM swizzle、每条指令的操作数形状，以及大 tile 上的多次指令重复。partition 将这些规则组合成可访问的视图，避免业务代码反复手写复杂下标。

这也解释了为什么 partition 不总是让元素数量变少：它可能选择一个参与者的子集，也可能把同一批元素重组为“指令内部坐标 × 指令重复次数”。是否减少元素，取决于参与者划分与指令规则。

3.6 partition_A/B/C 与 partition_S/D 的后缀

函数 根据哪种规则建立视图 后缀含义
partition_S Copy 的源端规则 S = Source，不是 SMEM
partition_D Copy 的目标端规则 D = Destination，不是 DRAM
partition_A MMA 的 A 操作数规则 A 是矩阵角色
partition_B MMA 的 B 操作数规则 B 是矩阵角色
partition_C MMA 的 C／结果坐标规则 不限定数据必须叫 C，也可用于输出 D
partition_shape_A/B 只计算对应的分组 shape 不需要已有数据指针

源端与目标端的 partition 都服务于同一批逻辑值，但具体 shape 和地址表达可能不同。例如 TMEM load 的源是 warp 协作操作数，目标是各线程自己的寄存器，不能要求两者打印出来完全相同。

3.8 回到 Blackwell：fragment 不一定保存浮点数

对本例的 SS UMMA，A 和 B 的数值在 SMEM 中，指令需要的是读取它们的描述符：

fragment 本例里表示什么 创建它时没有发生的事
tCrA / tCrB SMEM 输入描述符视图 没有把整个 A/B 读进数值寄存器
tCtAcc TMEM 累加结果的布局与视图 没有因此自动申请 TMEM，也没有读取 GMEM C
epilogue 的局部 fragment 每线程的数值存储 没有自动执行 GMEM/TMEM load

描述符本身可以保存在寄存器中，但保存的是地址和布局元数据，不是整个输入矩阵的浮点值。TMEM 视图则必须经过显式 allocation 并绑定 base，才能用于后续运算。

3.9 一轮 K64 怎样被 partition 成四个 MMA 子块？

本例 A 的单轮输入是 128×64。一条 UMMA 消费 A 的 128×16，所以这一轮需要四条指令：

例如同一个元素可以写成 A[37,39] 或分组坐标 A_view[(37,7),0,2]。这一步改变访问坐标，地址仍指向原来的元素。shape 从 (128,64) 组织为 ((128,16),1,4)：第一个 mode 是单条 MMA 的 A 操作数，第二个 mode 表示 M 方向的一次重复，最后一个 mode 表示四次 K16 重复。

随后输入 fragment 为这些子块提供对应描述符。执行 gemm 时，硬件依据描述符读取 SMEM 并更新 TMEM。partition 负责组织访问，fragment 提供指令需要的表示，gemm 才发起矩阵计算。

4. 线程排布：必须说明处于哪个阶段

本例的 block 是一维 128 线程。warp_id=tid/32，lane=tid%32。输出分块是二维的，但这不要求 CUDA block 也必须是二维。

对于 CTA(bx,by)，输出起点为 m0=128bx、n0=256by。同一 M tile 的不同 CTA 会读同样的 A 行，不同 N tile 则读不同的 B 行。本例没有 cluster multicast，也没有分布式共享内存协作。

同名 get_slice，坐标的含义不一定相同

第一行在这类 SM100 UMMA 中选择的是 peer CTA 。当前只有一个 CTA，合法坐标是 0。第二行在 TMEM 读回中选择的才是实际线程。ThrMMA 这个类型名不能替代对 atom 的 ThrID 的检查。

UMMA 的 ThrLayoutVMNK=(1,1,1,1) 描述 peer CTA 维度 V 及 MMA 在 M/N/K 上的组织；这里没有额外复制 atom。它不是 128 条 CUDA 线程排成了 1×1×1×1。

5. GMEM → tile → MMA view：地址完全可以不变

数学表达为 D[m,n] = α Σk A[m,k] Bphys[n,k] + β C[m,n]。为了使 K 连续，例子把 B 以 (N,K) 视角表示；若按通常 GEMM 记法写成 Bmath[K,N]，则 Bmath[k,n]=Bphys[n,k]。这个“转置”不要求先运行转置 kernel。

全局 tensor Shape : Stride（元素单位） 相对地址（字节）
mA (512,256):(256,1) 2×(m×256+k)
mB (1024,256):(256,1) 2×(n×256+k)
mC / mD (512,1024):(1024,1) 4×(m×1024+n)

make_tensor(make_gmem_ptr(ptr), layout) 把裸指针与坐标规则绑定，没有加载数据。local_tile 在这个大矩阵里选择 CTA 的区域。Step<_1,X,_1> 在 A 上保留 M、K 并忽略 N；B 保留 N、K；C/D 保留 M、N。

partition_shape_A/B 只计算需要的坐标形状，不需要数据指针；partition_A/B/C 在已有 Tensor 上生成相应视图。两个函数都没有搬运矩阵。

MMA 的 TVLayout 为什么是 (1,(128,16))？

外层是 (T,V)：这里 T 的大小为 1，表示 atom 的一个参与 CTA；V 又被分解成矩阵坐标。对 A，映射结果为 m+128q。它是 A 操作数的 逻辑编号 ，不是 GMEM 地址，也不是某个 lane 的寄存器编号。

例如 (m,q)=(37,7) 的 MMA 逻辑编号是 933。配合本轮 j=2,t=1，它对应 A[37,103]，其 GMEM 元素偏移是 9575。两个数不同，因为前者标识指令内的元素，后者标识全局内存位置。

6. SMEM：逻辑 shape 与物理 swizzle 同时存在

UMMA::tile_to_mma_shape(Layout_K_SW128_Atom<Type>{}, mma_shape) 为符合 UMMA 坐标分组的 SMEM Tensor 构造布局。本例 A 的逻辑 shape 是 ((128,16),1,4)，B 是 ((256,16),1,4)。忽略分组后，它们分别是 A[128,64] 与 B[256,64]。

在没有 swizzle 的基底里，A/B 都是 row×64+x 个 FP16。一行 128 字节，可拆成八个 16 字节包。Swizzle 会根据行号交换包的位置，不改变元素的数学坐标。

上式相对于各自 A 或 B 缓冲的起点，适用于这里的 K-major、FP16、K64、SW128 布局。Sw<3,4,3> 在这段打印中附着于字节寻址的 SMEM 引擎：将地址 bit[9:7] XOR 到 bit[6:4]，bit[3:0] 保持不动。不要看到 FP16 指针后，就直接对“元素 offset”的同样位段做 XOR；必须先统一单位。

基地址也参与 swizzle。 这里的 swizzle_ptr 对“base+offset”做置换，而不是无条件只置换 offset。一般形式是 u=base+128×row+2×x，physical=u XOR ((u & 0x380)>>3)。若 base 仅保证 128B 对齐，应使用 physical_pack=pack XOR ((base/128+row)%8)。本文数字图取基相位 0；不能只从 alignas(128) 推断必然满足这一简化条件。

每个逻辑元素都能沿布局写到正确物理位置，也能被带有匹配 swizzle 信息的 MMA 描述符重新解释。 SMEM 的非连续物理外观，并没有打乱数学上的 K 顺序。

从常见的 32-bank、每 bank 4B 的观察方式看，bank=(byte_address/4)%32。若每行相隔 128B，不做 swizzle 时相同列的不同 row 落在相同 bank；取基相位 0、x=0，row=0…7 经 swizzle 后分别映射到 bank 0、4、8、12、16、20、24、28。相邻两个 FP16 同属一个 4B word。这个例子说明 XOR 如何分散访问；具体指令是否发生 bank conflict，还要看它实际分阶段访问哪些地址，不能只数一张矩阵图就断言完全无冲突。

A 缓冲为 128×64×2=16 KiB，B 缓冲为 256×64×2=32 KiB，总数据容量 48 KiB，另有 barrier、TMEM base 元数据与对齐开销。alignas(128) 提供对齐；ArrayEngine<T,cosize_v<Layout>> 提供存储；make_tensor(make_smem_ptr(...),layout) 才提供访问这块存储的坐标接口。

谁搬运这个元素？再看 copy 的线程分工

这是依据2026-10-30 对照的 cooperative_copy.hpp 做的实例化分工推导：选择 SMEM 去掉 swizzle 后的连续次序，把 128 个线程放到 K64×两行中。无第二个模板实参的 cooperative_copy<128> 当前默认 MaxVecBits 为元素位宽，所以这里是 16 bit。源码注释中的 “auto-vectorized” 不能直接推断成每线程固定搬 16 字节。

改变 MaxVecBits、输入布局、类型、对齐约束或 CUTLASS 版本，copy 的线程划分可能改变。 copy 的线程划分不属于 UMMA 的数学约束；只要最后每个 SMEM 元素正确，发起矩阵指令的线程不必是搬入该元素的线程。

本例没有 TMA。普通 cooperative copy 会根据编译结果生成相应 load/store，可能经过临时寄存器。不要把这条输入通路与使用 TMA 的多阶段示例中的搬运混为一谈。

7. MMA：fragment 是描述符，累加结果在 TMEM

make_tiled_mma(SM100_MMA_F16BF16_SS<...128,256,Major::K,Major::K>{}) 选择一类矩阵指令并建立 CuTe 对它的布局描述。SS 表示本例两个输入都来自 SMEM。它既没有计算，也没有分配 TMEM。

make_fragment_A(tCsA) 与 make_fragment_B(tCsB) 生成的是 SMEM 描述符视图 。这里的 tCrA/tCrB 包含描述矩阵起点、步长、swizzle 等信息的元数据；不是把 128×64 个输入都加载进 CUDA 线程寄存器。

该描述符迭代中的步长 2，以 16 字节编码单位计量：前进一个 K16 子块，FP16 逻辑 K 位移是 16×2=32 字节，即 2 个编码单位。这是 描述符的地址增量 ，不能解释成“只前进两个 FP16”，也不能将它当成整个子块在 SMEM 中的总字节数。

单条指令的数学意义：

也就是说，每条指令都更新 32768 个结果；j 的变化是在同一结果平面上继续沿 K 求和，不是依次计算输出的四个象限。A 的一个元素会参与对应 m 行的多个输出；B 的一个元素会参与对应 n 列的多个输出。

warp 0 的所有 lane 进入 CuTe gemm 调用，包装器内部负责选择一个线程发出所需的单线程 UMMA 指令。不要把外层调用随意改成仅 lane 0 进入：包装器可能含 warp 级协作约定。

第一个 MMA 使用 ScaleOut::Zero，忽略旧累加值；之后全部使用 One，包括后续外层 K tile。若每轮 K64 都重新置 Zero，就只会留下最后一轮的结果。GMEM 中的 C 是 epilogue 的 βC 输入，不是这里被清零的 TMEM Acc。

8. TMEM：看见 stride=65536，先换地址单位

在这里使用的 SM100 接口中，TMEM 是 128 行、512 列的 32-bit 单元，按列分配。结果需要 128×256×4=128 KiB；示例为了简单请求了 512 列，也就是整个 256 KiB 容量。

这个地址是编码：高 16 位选择 TMEM 行，低 16 位选择列。+1 前进一个 32-bit 列，+65536 选择下一行。不能把它解读为行与行之间相隔 65536 字节，也不能拿它当普通 CUDA 全局指针。

make_fragment_C(tCgC) 先创建累加 tensor 的形状和 TMEM 布局。随后，warp 0 调用 allocator，硬件把 TMEM 基地址写到 SMEM 中的 tmem_base_ptr。全 CTA 同步后，tCtAcc.data()=tmem_base_ptr 才把地址接到视图上。

SMEM 里的 uint32_t tmem_base_ptr 只有 4 字节，是地址元数据，不是 128 KiB 的结果缓冲。分配、清零、计算也互不等同：本例用第一条 MMA 的 Zero 模式初始化累加结果，不是由 make_fragment_C 自动清零。

9. TMEM → 寄存器 → GMEM：这才出现逐线程结果归属

SM100_TMEM_LOAD_32dp32b1x 的 32dp 表示一次覆盖 32 个 TMEM 数据通路/行，32b 表示每行取 32 bit，1x 表示一次这样的重复。它按 warp 协作发出，返回的 FP32 按 lane 分给线程。本例四个 warp 分别读取行 0–31、32–63、64–95、96–127。

make_tmem_copy(atom,tCtAcc) 把这个读指令扩展到完整 accumulator。对本例的布局，最终是 row=tid，每条线程负责这一行的 256 列。它和输入 copy 的“线程负责一个 K 坐标、多行”是完全不同的分工。

源 view 的 shape 中出现 ((32,1),256,1,1)，目标寄存器 view 则是 ((1,1),256,1,1)。前者描述指令的 warp 集体源操作数，不能理解为每个线程私有地拿走 32×256 个值。硬件将每次读取的 32 个 FP32 分到 32 个 lane，因此每个线程每列只得到一个。

Copy Traits 的 TVLayout 用 bit 编号

对象 意义
ThrID = Layout<32> 这个 Copy atom 用 32 个 lane 协作。
SrcLayout = (32,1024):(0,1) 源线程坐标不改变逻辑源 bit 集合；每个 lane 使用一致的源操作数描述。
DstLayout = (32,32):(32,1) lane l 的局部 bit b 对应逻辑 bit 32l+b。
ValID = (32,32):(1,DP_b) 把逻辑 bit 分解为“单元内 bit”和 TMEM 行；DP_b=2²¹，是编码行步长 2¹⁶ 再乘 32 bit。
RefLayout 用来对齐 atom 源端与目标端的参考逻辑编号，不是第四块存储。

数值寄存器视图不是物理寄存器分配报告。 tDrAcc 逻辑上每线程有 256 个 FP32，tDrC 也有相应的 C 值。编译器可能做生命周期优化、拆分、调度，甚至 spill；不能据此断言最终占用恰好 256 个硬件寄存器。实际数量要看编译报告和机器码。

epilogue 的流程为：GMEM C → tDrC；TMEM Acc → tDrAcc；逐元素计算 tDrC=αtDrAcc+βtDrC；tDrC → GMEM D。它按同一逻辑坐标配对，C 与 Acc 虽然来源不同，仍对应相同的 (m,n)。

本例中相邻 lane 在固定 n 处访问 D 的相邻 行 ，地址差是 N×4 字节。因此“一个线程内部的 256 列连续”不代表“同一 warp 一次 store 合并良好”。更高性能 epilogue 可以换 copy 方式、重排或使用 SMEM 中转；本例主要展示 TMEM 接口。

10. 计算流水线：先画生命周期，再看 barrier

这是一条有异步指令的执行流程，但不是多阶段重叠流水。单份 A/B SMEM 的生命周期必须满足： 写完 → MMA 读取完成 → 才能重写。

  1. 准备： 创建各类 view、分配 TMEM；初始化一个 MMA barrier，arrival count 为 1。
  2. 加载第 t 轮： 128 线程 cooperative_copy A/B；__syncthreads() 保证相关线程写完 SMEM，之后才能启动读取它的 MMA。
  3. 发起： warp 0 依次调用四次 gemm，覆盖四个 K16 子块。发出指令与 Tensor Core 执行完成是两个时间点。
  4. 提交完成通知： umma_arrive 使用 UMMA completion 机制，把前面这组运算的完成关联到 barrier。
  5. 等待： 全 CTA 等待当前 phase 的完成，然后 phase 异或 1。此时上一轮 MMA 已不再读取这份 A/B，下一轮可以覆盖。
  6. 尾处理： 四轮共十六次 MMA 后读取 TMEM，完成 αAcc+βC；全 CTA 同步后，由分配 TMEM 的 warp 释放分配许可并释放 TMEM。

__syncthreads() 协调的是 CTA 线程；MMA completion barrier 追踪的是异步 Tensor Core 操作。仅仅所有线程走到同一点，不代表 Tensor Core 已执行完。反过来，MMA 完成通知也不能代替计算开始前对普通输入写入的同步。

这里的 phase=0,1,0,1 只是 barrier 第几次使用的奇偶状态。四轮加载、四个 K16 子块、两个 phase 值都不是 buffer 数量。本例只有一份输入缓冲；phase 改变不导致数据自动切换到另一个地址。

如果想改成重叠流水，必须先安排多份 SMEM，并分别约束“新数据可读”和“旧数据不再被消费”的时刻，然后才谈更多 stage。不能删掉 wait 后继续覆盖同一块 SMEM。

11. 把同一个坐标算到底

选取 CTA(0,0) 中的 A[37,103]×Bphys[69,103]，取 A/B SMEM 起点的 swizzle 基相位为 0，TMEM base=0。它对 Acc[37,69] 提供一个乘积贡献，但 Acc[37,69] 还要加上其他 255 个 k 的贡献。

12. 一眼判断封装函数到底做了什么

函数 / 对象 作用 是否移动矩阵数值？
make_shape / make_stride / make_layout 构造坐标范围、步长和映射函数。 否
make_gmem_ptr / make_smem_ptr 给指针附加存储空间等语义，供派发和寻址使用。 否
make_tensor(ptr, layout) 非拥有型的指针 + 访问规则。 否

make_tiled_mma 选择 atom 并建立矩阵指令组织规则。 否
get_slice 选择某个参与者；先辨明是 peer CTA 还是 CUDA thread。 否
partition_shape_A/B 只计算 MMA 所需的分组 shape。 否

变量名可以辅助阅读：mA 是完整矩阵，gA 是该 tile 的 GMEM 视图；tCgA 是施加 C/CTA-MMA 分块后的 GMEM A，tCsA 是 SMEM A，tCrA 在本例是 descriptor，tCtAcc 是 TMEM Acc；epilogue 的 tD… 是另一套 copy 分块。 字母前缀是命名习惯，engine 类型才是存储语义的依据。

13. Layout 代数：只改变坐标函数时，不发生数据搬运

composition：把两个函数接起来

假设 P 把小块坐标转成大矩阵坐标，L 把矩阵坐标转成地址，那么组合的含义就是 L(P(coord))。TV 到逻辑坐标再到地址，也是同样的思路。CuTe 对这些组合做编译期化简，所以不一定在机器码里真的保留这么多层调用。

logical_divide / tiled_divide：拆坐标，不切割存储

把长度 16 的连续向量按 4 拆分：i=inner+4×tile，新 Shape(4,4)、Stride(1,4)。实际元素仍在原内存位置。两者主要在结果 mode 的组织方式上不同；不要根据“divide”猜测会启动一个分块 kernel。

coalesce：合并可线性化的相邻坐标

(4,3):(1,4) 可以化为长度 12、stride 1，因为整个坐标域连续。(4,3):(1,8) 的行块之间有空洞，不能直接当作长度 12 的连续存储。合并需要满足实际映射关系，不是把所有 shape 相乘就完事。

product / tile：复制或扩展布局的结构

一个 atom 定义最小访问或计算单元。扩展布局描述这些 atom 如何重复、坐标如何组合。它本身不执行那些操作；只有后续 copy/gemm 按这个组织访问数据时，才出现实际重复。

inverse：从位置反推坐标，先确认是否可逆

一一对应的布局可以反推；带 stride=0 的广播布局会让多个坐标映射到同一个位置，就没有普通意义上唯一的逆。CuTe 的 right_inverse 等工具有具体的有效域与布局代数约定，不能把任何 layout 都当成满射双射。

recast：改变元素解释单位，不是数值类型转换

例如把两个 FP16 的 4 字节存储重新以 32-bit 容器描述，逻辑元素数量和 stride 单位可能改变，但不是把两个 half 各自转换成 float。真正数值转换要有对应运算；地址单位改变时必须重新检查 alignment 和 size。

读一段陌生 CuTe 代码，按这个次序： ① 确认数学 shape；② 看 engine 的存储空间；③ 写出坐标展开公式；④ 判断 TV 的参与者是 lane、warp 还是 CTA；⑤ 标明 stride 的单位；⑥ 找到实际 copy/gemm；⑦ 检查谁写、谁读、何时允许复用。

本图谱的 CPU 校验覆盖 A/B SMEM swizzle 的全范围双射、tile 与 MMA view 的 GMEM 地址等价、输入 copy 覆盖、TMEM 输出行列与读回线程覆盖，以及本文所有数值追踪。它不替代 GPU 编译与运行测试；当前未对本文配套说明做 GPU 编译运行验证，也未报告硬件寄存器数量或实测时序。
